## Build 31 — Date Ranges, Spoken-Time Extraction, Offline Local Notifications, Full-Detail To-Do Edit

Phase 2 Step 4. Commits `6b14c42` (the feature) and `a281906` (a same-session follow-up fix, see below).

**Schema**: `todos` gains `to_date` (nullable TEXT — end of a date span) and `notification_time` (TEXT NOT NULL DEFAULT '05:00'), via the same idempotent `ALTER TABLE ... ADD COLUMN` pattern every prior `todos` column addition uses. `db/schema.ts` exports `DEFAULT_NOTIFICATION_TIME` as the one place that default is authored, imported everywhere else that needs to know it (`transformationEngine.ts`, `todoManager.ts`, `TodoItemRow.tsx`, `AddTodoBottomSheet.tsx`) rather than duplicated as a literal.

**Deliberate deviation from the original brief, disclosed at the time**: the brief asked for a GBNF grammar exposing `from_date`/`to_date`/`notification_time` as separately-typed fields the model computes directly. That was NOT implemented that way — it would mean the model itself normalizing dates and splitting one range/time mention into independently-copied substrings, exactly the date-arithmetic unreliability this project already hit and fixed once before (commit `ca66581`: "pay rent on the 1st of every month" asked on Sep 9 came back `2026-11-01`, a month too far, when a 1B model computed it directly). Instead, the existing `date_phrase` field (see Build 30's chrono-node rework) now also carries a range ("27th Sep to 10th Oct") or a time ("at 3:30 PM") verbatim, and a new `resolveDateAndTime()` in `transformationEngine.ts` splits/resolves it deterministically via chrono-node's own native range/time-of-day support (`chrono.parse()`'s `.start`/`.end`, `.isCertain('hour')`) — same pre-pass-and-reconcile architecture, extended rather than replaced. Delivers every functional requirement (ranges, spoken-time extraction, 05:00 default) without reintroducing a proven regression.

**A second real bug found and fixed while rewriting that exact function**, not part of the original brief: chrono-node reads the bare number in "every 3 days" as "3 days from today" rather than recognizing a cadence with no specific start date — confirmed this was NOT limited to the auto-fill path Build 30 already gated by recurrence, but present whenever the model correctly writes a numeric-interval phrase into `date_phrase` at all (i.e. exactly the case Build 30's own new few-shot example was teaching it to do). Fixed by having `resolveDateAndTime()` ignore chrono's date component — falling back to today, still honoring any genuine explicit time — specifically when recurrence isn't "none" AND the phrase matches a bare numeric interval (`NUMERIC_RECURRENCE_INTERVAL_PATTERN`, shared with `resolveRecurrenceInterval`'s own matching). Deliberately narrow: "every Monday"-style phrasing, where chrono's next-weekday resolution is a reasonable default start date, is left untouched.

**Notifications** (`services/notifications/`): `notificationHandler.ts` (new) is the one app-wide `Notifications.setNotificationHandler` call for the whole app, extracted out of the pre-existing `downloadNotification.ts` — expo-notifications only accepts one handler total, so a second inline call from the new `todoNotifications.ts` would have silently replaced the download-progress mirror's silent behavior depending on which module happened to import first. It branches on `content.data.kind`. `todoNotifications.ts` (new) schedules/cancels a to-do's own local Android notification on its own `"todo-reminders"` channel (`DEFAULT` importance + sound — deliberately NOT the download channel's silent `MIN`), keyed by a stable per-todo identifier so rescheduling naturally supersedes an old trigger; a tap-response pub/sub (`subscribeToToDoNotificationTap`) opens the To-Dos overlay, wired into `app/index.tsx`'s startup effects alongside a new `initializeToDoNotifications()` permission/channel priming call. `todoManager.ts`'s `addToDo`/`updateToDo`/`completeToDo`/`deleteToDo` all call into this — `completeToDo`'s recurring respawn preserves a range's LENGTH (not its absolute end date) across occurrences.

**`addToDo` converted from positional params to an options object** (`AddToDoInput`) rather than growing to 7 positional arguments — `updateToDo` already took this shape. Both call sites (`TodosOverlay.tsx`, `noteManager.ts`'s extraction pipeline) and the `useToDos()` hook wrapper updated accordingly.

**UI**: `AddTodoBottomSheet.tsx` gained "To Date (optional)" and "Notification Time" sections, same quick-pick-chips-plus-"Custom"-field pattern as the existing date picker (no new native dependency). `TodoItemRow.tsx` renders a date-range line ("📅 27 Sep – 10 Oct 2026") when `to_date` is set, and a time badge ("⏰ 3:30 PM") when `notification_time` isn't the 05:00 default.

**A same-session gotcha, not a code bug**: after this shipped, the user hit `sqlite query error: no such column: to_date` repeatedly on-device. Root cause: `db/client.ts` caches its `op-sqlite` connection on `globalThis` specifically so Fast Refresh doesn't repeatedly re-open/re-key the database — which also means a brand-new migration only runs on the next real app **process** start, not on the next JS hot-reload. The user had been testing via Fast Refresh since the commit landed, so the already-open connection never got a chance to run the new `ALTER TABLE` statements. Fixed with no code change at all — `adb shell am force-stop` + relaunch — confirmed via logcat that the error stopped appearing afterward. Documented as a standing troubleshooting note in CLAUDE.md so it isn't re-investigated as a real bug next time a schema migration ships.

**On-device verification, both confirmed working by the user directly**:
- Voice note "Remind me for Lexi's pet hosting from 12th Nov to 14th Nov at 3 PM." → saved with `actionDate = 2026-11-12`, `toDate = 2026-11-14`, `notificationTime = 15:00`, exactly as expected.
- A manually-created "testing" to-do with a reminder set 2 minutes in the future fired its Android notification at exactly that time.

**Follow-up in the same build** (commit `a281906`): the user asked to edit a to-do's full details, not just its text (the only thing the existing edit-pen inline `TextInput` could touch). Rather than build a second editor, `AddTodoBottomSheet` now doubles as the editor via a new optional `editingTodo` prop — `TodosOverlay` tracks `editingTodo: ToDo | null` alongside its existing `isAddVisible` state, and `TodoItemRow`'s edit pen (previously toggling a local inline-edit `TextInput`, now removed entirely) calls a new `onEditDetails(item)` prop instead. Opening pre-filled derives each field's "Custom" chip state by checking whether the saved value matches one of that field's own quick-pick presets. One `onSave` callback shape serves both modes; `TodosOverlay` is the only place that branches between `addToDo`/`updateToDo`. Confirmed working by the user ("works like expectation").

`npx tsc --noEmit` / `npx expo export --platform android` clean throughout. No new native dependency — `expo-notifications` was already linked (Build 25) — every change in this build is pure JS/TS, reachable via Fast Refresh with no `prebuild`/`run:android` cycle required (aside from the process-restart gotcha above, which is about the cached DB connection, not native linking).

## Build 30 — To-Dos Freeze Root-Caused & Fixed, Overlay Rebuild, Add-Todo Sheet Keyboard Saga, Chrono-Based Date Extraction (unversioned)

Phase 2's "Your To-Dos" module (auto-structured to-dos extracted from note text, plus manual add) shipped as commit `d45b950`. Everything below happened after, across one long session, in the order it actually happened.

### Total freeze bug — root cause found, fixed

Opening/using the To-Dos screen on the test device would go **completely unresponsive** — no checkbox, edit, +, back, or scroll — with no crash, no exception, and the JS thread reporting idle. Touches kept dispatching at the OS level but never reached React. This looked, and was investigated, like a UI bug for most of the session.

**UI-layer hypotheses investigated and ruled out, in order** (each a real, defensible fix that stayed in the codebase, but none was the actual cause): `@gorhom/bottom-sheet` dynamic-sizing/fixed-snap-point combinations; a `Keyboard.addListener` + `FlatList.scrollToIndex` fix for a keyboard-covers-input issue; RN's core `<Modal>` opening on a **pushed** `expo-router` route (theorized as an Android `react-native-screens` Fragment-focus bug — fixed anyway by converting `/todos` from a pushed route into `components/TodosOverlay.tsx`, a full-screen root-sibling overlay matching the existing `ExpandedTextOverlay` pattern, commit `4cefbcc`); touchable/gesture-handler harmonization (`Pressable` → `TouchableOpacity` from `react-native-gesture-handler` throughout `TodoItemRow.tsx`/`TodosOverlay.tsx`, since this app's `GestureHandlerRootView` root also hosts `@gorhom/bottom-sheet`, commit `ae12374`). A production EAS preview build (sideloaded directly, bypassing Metro/dev-client entirely) still froze — ruling out the dev client as the cause and forcing the investigation back to first principles.

**Actual root cause, found via `adb logcat` timing analysis**: `services/ai/localLlama.ts` hardcoded `n_threads: 4` for the shared Llama context (used by both interactive RAG chat and background to-do extraction), on the wrong assumption the test device "has 4 usable cores" (a new native module later confirmed it's actually 8 — Exynos 9610). A GBNF-grammar-constrained to-do extraction was measured taking **140+ seconds**, during which those 4 dedicated inference threads starved the OS's own input-dispatch/render threads of CPU time — a full-app freeze for the entire extraction duration, misread as a UI bug because there was no crash and the JS thread itself was genuinely idle (it wasn't JS that was blocked, it was systemwide CPU contention).

**Fix** (commit `ae2f8ac`): added `modules/device-cpu/` — a tiny local Expo native module wrapping Android's `Runtime.getRuntime().availableProcessors()`, following the exact pattern of the pre-existing `modules/app-signature/` — and changed `localLlama.ts` to size `n_threads = Math.max(1, Math.floor(cores / 4))`, a **proportional** reservation (a quarter of cores for inference, three-quarters left for the OS/UI), computing 2 threads on the 8-core test device (down from the hardcoded 4). A real regression was caught and corrected mid-session before being reported as fixed: an earlier attempt reserved a **flat** number of cores (`cores - 2`), which computed *worse* results (6 threads) on this actual 8-core phone than the original bug — worth remembering for any future device-sizing decision, and the direct reason the fix uses a proportion of cores rather than a flat headroom count (the user explicitly pushed back on tuning the code to one test phone: "this phone isn't the barometer"). Sub-finding: `llama.rn`'s `CompletionParams.n_threads` (a per-call override) does **not** work — confirmed against `llama.rn`'s native C++ source that the ggml threadpool is attached once at `initLlama()` time and nothing calls `llama_set_n_threads()` per completion, so a per-call override for extraction alone (tried and reverted) is a silent no-op; one shared, conservative context-level thread count is the only real lever, slowing down both RAG chat and extraction as an accepted tradeoff.

**Confirmed fixed on-device**: checkbox, edit, +, Source Note, and back all working after commit `ae2f8ac`.

2. `bottomInset` prop on `<BottomSheet>` instead (`bd2faf8`) — same break.
3. Fixed `snapPoints=["50%"]` + `enableDynamicSizing={false}`, matching `HistorySheet.tsx`'s own proven setup, with the nav-bar inset moved to plain trailing padding around just the Save button (`f94f3f9`) — the sheet's title now cleared the keyboard, but the input further down still didn't: a 50%-tall sheet plus a keyboard that itself eats ~40–50% of the screen leaves no vertical budget for every stacked field to be visible at once.
4. `BottomSheetScrollView` instead of a plain `View`/`BottomSheetView` (`0fbc83c`) — still didn't clear the input; `keyboardBehavior="interactive"` translates the sheet as a whole but doesn't auto-scroll a specific focused field within a scroll container.
5. **Fix that held**: `SNAP_POINTS` bumped to `["90%"]` (`160ccca`) — sidesteps needing the interactive-positioning math to be exact at all, by giving the title/input enough plain headroom near the top of a near-full-screen sheet that no keyboard height reaches them regardless. ### To-Do date extraction — chrono-node pre-pass replaces per-miss few-shot growth

A reported "to-dos always land on today regardless of what date the note actually said" bug was root-caused via a temporary raw-input debug log (removed once diagnosed — this app deliberately never logs raw note content elsewhere, see `noteManager.ts`) to a real model-accuracy miss, not a chrono-node resolution bug: a bare imperative voice-note transcript ("Book a movie ticket this Friday.") consistently (temperature 0, fully reproducible) got back an empty `date_phrase` from the 1B extraction model, despite an existing few-shot example with the same date phrase in a different sentence shape.

The user correctly identified that "add one more few-shot example per miss" doesn't scale — unbounded prompt growth, worse mobile TTFT, and it only ever covers phrasing shapes someone happened to hit. **Architectural fix** (commit `334a667`): `detectDatePhrases()` runs `chrono-node`'s `parse()` (not just the existing `parseDate()`) directly on the raw note text **before** the LLM call, independent of the model entirely, and the result is injected into the system prompt as an "answer key" the model is told to copy from exactly. `normalizeExtracted()` then reconciles the model's own `date_phrase` against that same list rather than trusting it outright: a phrase that's neither in the detected list nor a literal substring of the note anywhere is dropped as a hallucination (a new safety net); an empty `date_phrase` on a single-task, non-recurring note where chrono found exactly one candidate is auto-filled with that candidate — the deterministic fix for the exact reproduced miss. Considered and rejected: a dynamically generated GBNF grammar restricting `date_phrase` to exactly the detected phrases (correct in principle, but fragile to hand-write correctly — nested GBNF/JSON string escaping — versus the reconciliation approach's much simpler, more obviously correct code for the same practical guarantee). Performance: `detectDatePhrases()` is synchronous JS on the JS thread (single-digit ms), zero interaction with the shared llama.cpp context or the `n_threads` tuning above; the prompt grows by a handful of tokens, noise against the existing several-hundred-token preamble.

**A regression this introduced, found and fixed in the same pass** (commit `6e59636`): chrono has no concept of a recurrence *cadence* — "Water the plants every 3 days." classified recurrence "daily" correctly, but chrono detected the fragment "3 days" (from inside "every 3 days") as its own one-off relative date, and the single-candidate auto-fill trusted it, producing a wrong one-off action date ~3 days out instead of respecting the recurring schedule. Fixed by resolving recurrence *before* date-phrase reconciliation and only auto-filling from chrono's detection when `recurrence === "none"` — chrono only ever detects calendar dates, never cadences, so its candidates are only trustworthy for non-recurring tasks. Also added a dedicated few-shot example retaining a purely numeric interval phrase ("every 3 days") in `date_phrase`, since no prior example demonstrated that shape and it's the one thing chrono structurally cannot backstop (a cadence phrase can only ever reach `date_phrase` via the model getting it right).

**A deliberate 7-note edge-case test pass found two further failures, one fixed/mitigated and one left open**:
- A numeric-interval note ("every 3 days") — the regression above, now fixed.
- A false-recurrence-trap-word note with two real candidate dates (an expiry date and the actual action date, mirroring the existing "Shivanya's passport" few-shot almost exactly) — the model hallucinated a nonsense phrase instead of picking the correct one of the two from the hint list; correctly dropped by the hallucination guard, but fell back to "today" rather than the right date. Mitigated (not solved) by strengthening the hint instruction for the 2+-candidate case; **left open** as a likely real accuracy ceiling for a 1B on-device model on hard multi-date disambiguation, rather than something more prompt tuning can reliably fix without reintroducing the unbounded few-shot growth this whole redesign was meant to avoid.
- A multi-task note ("Call the electrician, pick up dry cleaning, and also renew my gym membership by Friday.") — the one trailing date wasn't attached to any of the three tasks even with the hint list present. This is a task-to-date *assignment* judgment call chrono has no way to make (it has no concept of "task"); mitigated with one new few-shot demonstrating the common "trailing date modifies only the last-mentioned task" pattern (commit `6e59636`), **not yet re-verified on-device** — the user opted to pause testing here and revisit later rather than re-test immediately.

`npx tsc --noEmit` and `npx expo export --platform android` clean throughout this build's commits. All changes were pure JS/prompt/TS — no native dependency touched, verified live via Fast Refresh on the physical A50, except `modules/device-cpu/` (a new native module, required a real `prebuild`/`run:android` cycle, done and confirmed linked). ## Build 29 — Bidirectional Pill Sync, Monochromatic Glass Expandable Notes Container

Four passes on top of each other, the last three all against the same new feature — kept as one build section since they were delivered together, but broken out below in the order they actually happened, including the two real bugs found only after the first version looked done.

**Bidirectional tab-pill sync (real bug, found by audit, not reported by the user)**: `app/index.tsx`'s Build 23 comment claimed the floating `[Record | Ask]` pill and the drawer's `Recorded notes`/`Searched notes` segment control stayed "in lockstep the moment the pill itself is tapped" — true only in one direction. The drawer segment pill was wired straight to the raw `setHistoryTab` setter (`onHistoryTabChange={setHistoryTab}`), so tapping it flipped which list was visible but left `inputMode` — and the floating pill's own highlighted state — untouched. Concretely: switch to Record, tap "Searched notes" to browse old Q&A, then submit a new query — `routeFreeformInput` only ever reads `inputMode`, which never moved, so it would silently try to save a note instead of asking a question. Fixed with a new `handleHistoryTabChange` mirroring `handleSelectMode` in the other direction, so either pill now drives both. `npx tsc --noEmit` clean. Committed as `3213248`.

**Monochromatic Glass container, first version** (commit `c14b076`): a translucent `rgba(18, 18, 26, 0.65)` box (1px `rgba(255,255,255,0.12)` border, 18px radius) wrapping whichever list (Recorded/Searched notes) is active, with a 32px circular micro-chip top-right (`@expo/vector-icons`' Feather `arrow-up-right`/`x`) toggling between the sheet's existing 50% stage and a new 88% "expanded" stage reached via `snapToPosition("88%")` outside the sheet's configured `snapPoints`, plus spring physics (`useBottomSheetSpringConfigs`) shared across every snap this screen makes.

**Chip/text overlap, gesture-escape, and partial-expose fixes** (commit `b23f95f`) — three real bugs found immediately on-device:
- The chip overlapped the first note/message card's text — fixed with a dedicated top-clearance wrapper around the list content (chip's own 44px bottom edge + a 12px gap), kept structurally independent of the box's status-bar-clearing inset so the gap reads identically whether the chip shows the arrow or the cross.
- A plain swipe-up from 50% could reach 88% too — not just the chip — because 88% had briefly been a real `snapPoints` entry before settling on `snapToPosition`; keeping it a `snapToPosition`-only target hard-clamps the gesture's own range back to `[20%, 50%]`, with the chip's one discrete, always-fully-animated call the only path past it.
- That same `snapToPosition` excursion surfaced a subtler bug: `@gorhom/bottom-sheet`'s own index math doesn't clamp at the highest real snap index the way it does for an in-range drag — it pulls the reported index toward an internal "closed" anchor near full container height instead, which made this component's `sheetIndex > 0` render guard go false and unmount the entire box mid-transition (confirmed on-device: the sheet visually at 88% with nothing rendered below the sticky header). Fixed by gating that condition on a new explicit `isExpanded` boolean app/index.tsx owns, never subject to that index math.

**The actual architecture fix** (commit `c70efef`) — two more real bugs, and the reason the feature ended up rebuilt:
1. **The box only ever filled about the top half of the screen at 88%**, confirmed by reading `@gorhom/bottom-sheet`'s own `BottomSheetContent.tsx`: its content-area height calculation (`animatedSheetHeight = containerHeight - highestDetentPosition`) is deliberately capped at the highest *configured* `snapPoints` entry — the extension logic that lets content grow past that only fires for the library's own keyboard-avoidance cases, never for an arbitrary `snapToPosition` target. The box's `flex: 1` had nothing more than the 50% height to fill, and the clip happens inside a library-owned ancestor (`overflow: "hidden"`) no styling on our side can reach past.
2. The compose bar and drag handle stayed visible at the top of the expanded stage, which is exactly backwards for a "focus mode" view.

Both are symptoms of one problem: treating "expanded" as a literal stage of the bottom sheet at all. The fix is `components/ExpandedTextOverlay.tsx` — a new, plain `position: absolute` full-screen component, rendered by `app/index.tsx` as an ordinary sibling of `<HistorySheet>`, completely outside `@gorhom/bottom-sheet`'s state machine. Its own `flex: 1` glass box has no library-imposed ceiling to fight, and the sheet's compose bar/handle are structurally a different component it simply paints over — the sheet itself just stays wherever it already was (50%, since that's the only place its own chip lives) underneath. `HistorySheet`'s own micro-chip now only ever shows the arrow and only ever calls `onToggleExpand`; it has no "expanded" rendering of its own left to maintain. This also resolves the swipe-gesture concern from a cleaner angle: `snapPoints` stays permanently at `["20%", "50%"]`, with no `snapToPosition` excursion at all, so there is structurally nothing above 50% for a gesture to ever reach.

One more real bug surfaced building the overlay: `NotesSheetContent`/`ChatSheetContent` both hard-used `BottomSheetFlatList`, which reads React context (`useBottomSheetInternal`) only provided inside a real `<BottomSheet>` tree — mounting either inside the new plain overlay threw immediately (`'useBottomSheetInternal' cannot be used out of the BottomSheet!`, seen directly in a Metro red-box, not assumed). Both components now take a `usePlainList` prop that swaps in an ordinary RN `FlatList` when true; the overlay's own copies pass it, `HistorySheet`'s copies don't (keeping `BottomSheetFlatList`'s gesture-coordination benefit at the sheet's own 50% stage).

**Verified on-device at every stage**, including two testing-environment traps worth recording so they're not mistaken for app bugs next time: (1) this long-running Metro session's transform cache went stale more than once mid-build (a documented recurring issue for this project — see the CLAUDE.md troubleshooting note), surfacing as red-box errors referencing already-fixed code; resolved each time by killing Metro, deleting `%LOCALAPPDATA%\Temp\metro-cache*`, and restarting with `--clear`; a fresh `expo export` was used as a cache-independent ground truth to confirm the code itself was fine before chasing further. (2) The Expo dev client's own floating "Tools" debug bubble (dev-build only, never present in a real release APK) sits in the same top-right corner as this feature's chip and silently intercepted `adb`-driven taps there; dragging the bubble aside (or targeting a coordinate outside its hit region) was needed to keep testing the app's own chip.

`npx tsc --noEmit` clean throughout. Commits: `3213248`, `c14b076`, `b23f95f`, `c70efef`.

## Build 28 — Duplicate Voice RAG Query Fix (unversioned)

A real bug reported directly against a running on-device build, then root-caused via a live Metro log rather than assumed from the code: asking a spoken question in Ask mode produced **two** full RAG/Llama answers and two user/assistant chat bubbles for one utterance.

- **Root cause, confirmed via a live device log, not guessed**: `app/index.tsx`'s `finishUtterance` called `routeFreeformInput(...)` — which, for the ASK intent, already runs the complete RAG exchange via `chatSession.submitQuery()` (search, Llama generation, append a user+assistant message pair, everything) — and then, once that had already returned, called `chatSession.ask()` a **second time** on the identical transcript. That second call re-ran the entire pipeline from scratch and appended its own redundant message pair. A live log confirmed it directly: two full `SQLite-vec + FTS5 search retrieval` + `Llama total generation` cycles back to back for one spoken question (140s then ~10s — the second one faster only because llama.rn's context was already warm from the first).
- **Why none of Build 25's Atomic Voice Lock guards caught this**: `isSendingRef`/`isProcessingVoiceQueryRef`/`lastVoiceQueryRef` all guard against two *concurrent* calls racing each other on a stale closure. This bug's two calls are strictly *sequential* — the second one starts only after the first has fully finished and every ref/state guard has already reset — so it was never the race those defenses were built for.
- **Fix**: `routeFreeformInput`'s ASK branch now checks whether the call is voice-sourced (`audioUri` present). If so, it calls `chatSession.ask()` directly (the side-effect-free variant, no auto-speech) and returns the answer text to the caller; `finishUtterance` uses that returned text to speak the answer itself via `speakTextAndWait`, and no longer calls `ask()` a second time on its own. A typed (non-voice) ASK is unaffected — it still goes through `submitQuery` exactly as before, since ComposeBar's submit handler never called `ask()` afterward in the first place.
- `npx tsc --noEmit` — clean. Pure JS/TSX change, no native dependency touched — verified live via Metro's fast-refresh reload on the physical A50 (no `prebuild`/native rebuild needed).

## Build 27 — Fixed Silent Notifications Actually Reaching the Silent Channel (unversioned)

Four requested notification fixes, one of which uncovered a real, previously-invisible bug that explains why Build 26's "silent notification" work never actually worked on-device.

- **Disable launcher app badge**: `badge: 0` added to every posted notification's content, alongside the existing `shouldSetBadge: false` in the global handler and `showBadge: false` on the channel — three independent layers against the home-screen icon ever showing a count.
- **Silent channel importance**: `AndroidImportance.LOW` → `MIN` — `MIN` is what actually collapses a notification into Android's dedicated "Silent" shade section (confirmed on-device, see below) rather than merely suppressing its heads-up popup while still showing with visual weight.
- **Progress update throttling**: a native `scheduleNotificationAsync` call now only fires when the rounded percent has moved by at least 5 points since the last one actually shown, or 3 seconds have elapsed — whichever comes first — rather than on every ~250ms progress tick. Self-contained in `downloadNotification.ts`; no change to `modelDownloadManager.ts` was actually needed since it already hands every status change to the same one function.

## Build 25 — Atomic Voice Lock (Duplicate Voice Query / Double RAG Response Fix)

Not a versioned/EAS build — no `versionCode` bump was requested for this pass, so it exists only as local commit `a20a8f7` on top of Build 24. Fixes a real bug: a single spoken question could produce two user/assistant message pairs and two RAG/Llama runs.

## Category B, Item 8: Shower / Hands-Free Active Mode

- **`services/audio/wav.ts`** (new): `buildWavHeader`, `writePcmChunksAsWav`, and the shared `SAMPLE_RATE`/`CHANNELS`/`BITS_PER_SAMPLE` constants were extracted out of `services/audio/recorder.ts` into their own module, plus a new `computeRms()` helper. Both `recorder.ts`'s manual mic flow and the new `activeMode.ts` auto-segmenting loop needed the exact same WAV-assembly logic; `recorder.ts` was refactored to import it rather than keep a second copy.
- **`services/audio/activeMode.ts`** (new): `ActiveModeManager` — a framework-agnostic class driving the continuous "listen → auto-stop on silence → hand off to caller → re-arm" loop, plus a `useActiveMode(onUtterance)` React hook wrapping it for screen components.
  - **VAD approach and its real limitation, stated plainly**: silence detection is a simple RMS (root-mean-square) energy threshold over each incoming PCM chunk — `computeRms()` in `wav.ts`. This is *loudness-based*, not voice-based: it distinguishes "something loud is happening" from "it's quiet," not "that's a voice" from "that's noise." For an ordinarily quiet room this works fine as hands-free VAD. For the feature's own namesake use case — an actual running shower — continuous water noise sits close to white noise and can be loud enough to never drop below the threshold, meaning silence-based auto-stop may not reliably trigger while water is running. A genuinely shower-robust VAD would need spectral/energy-in-speech-band analysis or a real ML VAD model; neither is implemented. Flagging this now rather than letting "Shower Mode" imply it was solved.
  - Utterance boundary: `SILENCE_RMS_THRESHOLD = 0.02`, `SILENCE_HOLD_MS = 1500` (per the task's 1.5s spec), `MIN_UTTERANCE_MS = 400` (guards a stray tap/cough from finalizing as a real utterance), `MAX_UTTERANCE_MS = 60_000` (safety cap for a miscalibrated/noisy environment that never reads as "silent"). All named constants at the top of the file — tune there if the threshold needs adjusting for a real device/environment (untested against actual shower acoustics).
  - **No echo cancellation exists anywhere in this stack.** The critical consequence: the mic must not be capturing while the app itself is talking, or it will "hear" and transcribe its own TTS output as the next utterance. `ActiveModeManager` handles this by fully stopping the PCM capture session before calling `onUtterance`, and not re-arming until that handler's returned promise resolves — the handler is expected to `await` its TTS all the way to completion (see `speakTextAndWait` below), not fire-and-forget it.
  - **`services/audio/tts.ts`** gained `speakTextAndWait()` — `speakText()` itself resolves as soon as `Speech.speak()` is *called*, correct for the existing manual-chat UI (nothing there needs to block on narration finishing) but wrong for Active Mode, which must block the whole loop until speech actually finishes. Guards against the empty-text case, where the underlying `Speech.speak()` call is skipped entirely and its callbacks would otherwise never fire, which would have left the returned promise hanging forever.
  - **Android foreground keep-alive**: implemented via `expo-keep-awake` (installed as a direct dependency — it existed only as a nested transitive dependency of the `expo` package before this pass, not directly importable). `activateKeepAwakeAsync()`/`deactivateKeepAwake()` are tied to Active Mode's own start/stop. **Scope of what this actually covers, stated plainly**: this keeps the screen and CPU awake only while the app is in the foreground — it prevents the device from auto-locking mid-listen, which is the actual "shower" failure mode (phone screen timing out while your hands are wet/busy). It does **not** implement a true Android foreground service, so backgrounding the app or a manual power-button lock still suspends recording. A real background-capable service is a separate, materially larger native undertaking (persistent notification, foreground service permission/type, `expo-task-manager` or a custom native module) — not implemented here, and not what "keep-alive" was scoped to mean in this pass.
- **`components/ActiveModePill.tsx`** (new): the "soft toggle pill" from the task spec, rendered identically on both Notes and Chat headers (same position on both, following the Category A central-mic-button precedent), showing Listening…/Thinking…/Speaking… based on `ActiveModeManager`'s state.
- **Per-tab behavior**:
  - **Notes tab** (`app/index.tsx`): utterance → `asrRouter.transcribe()` → `createVoiceNote()` → `refreshNotes()` → `speakTextAndWait("Saved.")` → re-arm. Silent/empty transcripts are skipped with no note created and no spoken feedback (avoids narrating "Saved" for a false-positive VAD trigger with nothing actually said).
  - **Chat tab** (`app/chat.tsx`): `handleSend`'s message-creation and RAG-generation logic was extracted into a shared `runRagExchange()` so both the manual send flow and Active Mode append to the same visible chat transcript and hit the same code path — utterance → transcribe → `runRagExchange()` → `speakTextAndWait(answer)` → re-arm.
  - Both screens disable their manual mic button (and Chat additionally disables the text input/Send button) while Active Mode is engaged, since `@fugood/react-native-audio-pcm-stream` supports only one capture session at a time and `ActiveModeManager` owns its own session independent of `useVoiceRecorder`.
  - Errors during an Active Mode utterance are logged, never surfaced via `Alert` — a hands-free loop shouldn't interrupt itself with a dialog the user may not be positioned to dismiss (wet hands, phone across the room). The loop always re-arms in a `finally`, so one failed utterance doesn't end the session.
- `npx tsc --noEmit` — clean, zero errors.

```
java.lang.NullPointerException: Attempt to invoke virtual method 'int android.media.AudioRecord.read(byte[], int, int)' on a null object reference
  at com.imxiqi.rnliveaudiostream.RNLiveAudioStreamModule$1.run(RNLiveAudioStreamModule.java:103)
```
Root cause, found by reading the native source directly: `@fugood/react-native-audio-pcm-stream`'s background recording thread re-reads a shared **mutable instance field** (`recorder`) fresh on every loop iteration instead of capturing a stable local reference at thread-start. A concurrent `stop()`/re-`init()` (from a second recording session starting before the first thread has fully exited — a real scenario any time a session is stopped and quickly re-armed, exactly what Active Mode's loop does) can null or reassign that field mid-loop, so the next `.read()`/`.release()` call NPEs. This is a genuine upstream thread-safety bug, not something fixable from the JS side — no amount of delay/sequencing in `activeMode.ts` prevents a race that lives entirely inside the native module's own `Thread.run()`.

**Fixed via `patch-package`**, following this repo's established convention for broken native dependencies (see CLAUDE.md): `RNLiveAudioStreamModule.java`'s recording thread now captures `recorder` into a `final` local (`activeRecorder`) once at thread-start and operates on that stable reference for its entire lifetime, only clearing the shared field in its `finally` block if it still points at the same object (so a newer session's recorder is never clobbered by an older thread's cleanup). Patch lives at `patches/@fugood+react-native-audio-pcm-stream+1.1.4.patch` (54 lines — clean, targeted diff, no build-cache noise per the CLAUDE.md warning about that). Verified the fix with an incremental rebuild (`npx expo run:android`, no `prebuild --clean` needed since this was a Java-only change — `BUILD SUCCESSFUL in 43s`, confirmed `fugood_react-native-audio-pcm-stream:compileDebugJavaWithJavac` actually recompiled rather than reusing cache) and then stress-tested with 5 rapid on/off toggles in a row on-device — same PID survived throughout, zero crash traces in logcat afterward. The original bug was a timing-dependent race (not deterministic), so the repeated-toggle stress test matters more here than a single clean pass would.

## Category B: Multi-Tier ASR Router & Dynamic Llama 3B Model Loading

- **New native dependency**: `expo-speech-recognition@56.0.1` (publisher `jamsch`, actively maintained, versions track Expo SDK numbers). Verified via `npm view` before installing per this repo's package-provenance rule. **Caveat**: no `57.0.0` release exists yet as of this pass (project is on SDK 57, package's newest is SDK-56-aligned) — installed `latest` (56.0.1) since peer deps are unpinned (`"expo": "*"`), but this is unverified against SDK 57 and should be smoke-tested carefully on the first native rebuild. Config plugin added to `app.json` (`microphonePermission`, `speechRecognitionPermission`, `androidSpeechServicePackages: ["com.google.android.googlequicksearchbox"]`).
- **`services/ai/asrRouter.ts`** (new): unified two-tier ASR abstraction.
  - **Tier 1 (native)**: Android's on-device `SpeechRecognizer` via `expo-speech-recognition`, gated behind both `isRecognitionAvailable()` **and** `supportsOnDeviceRecognition()`, and started with `requiresOnDeviceRecognition: true`. The `supportsOnDeviceRecognition` gate is deliberate, not optional — this project's core loop must never silently depend on a network call (see CLAUDE.md), and this package's default mode is network-backed (Siri/Google servers). If a device only offers network-based recognition, Tier 1 is treated as unavailable and every note falls through to Tier 2.
  - **Tier 2 (local Whisper)**: unchanged `transcribeAudioLocal()` (`ggml-base.en.bin`), now called only from inside the router rather than from `noteManager.ts`/`app/chat.tsx` directly.
  - **Concurrency design decision**: Android's native `SpeechRecognizer` and the existing raw-PCM capture in `services/audio/recorder.ts` are two independent audio-input sessions, and whether a given device tolerates both holding the mic at once is OEM-dependent — there's no reliable way to know without hardware testing. Rather than pick one exclusively (which would mean either losing note playback audio, since PCM capture is what produces the WAV file every note plays back, or giving up the native tier's speed/accuracy benefit), the router starts Tier 1 *alongside* the unchanged PCM recorder and falls back to Tier 2 on the already-recorded WAV file if the native session errors, times out, or returns nothing. Every failure path in `asrRouter.ts` is written to fail into Tier 2, never to fail closed — a note is never lost because Tier 1 didn't cooperate on a given device. ## Post-Phase-4 Runtime Fixes — found and fixed via actual on-device testing

Phase 4's earlier "100% COMPLETE" declaration was based on a successful native **build** (compiles and links) — that's a weaker claim than "actually works." Two real runtime bugs surfaced once the app was actually exercised on-device, and both are now fixed **and confirmed live**, network off, on the `Pixel_6` emulator:

**1. ONNX crash: `[TypeError: Cannot read property 'install' of null]`**
- Root cause: `onnxruntime-react-native` ships an `app.plugin.js` (Gradle/Podfile dependency wiring only). Expo's autolinking treats any package with an `app.plugin.js` as "self-handled" and skips it from the classic community-autolinking pass that generates `PackageList.java` (the file that actually registers native modules on the bridge). So `OnnxruntimeModule` never got registered despite its C++ code compiling fine — `NativeModules.Onnxruntime` was `null` at runtime, crashing on `Module.install()`. The two Metro "Route is missing the required default export" warnings on `chat.tsx`/`index.tsx` were a downstream symptom, not a real bug — both files genuinely have `export default`; a module-scope import throwing during evaluation poisons the whole route's module graph before Metro can inspect its exports.
- Fix: project-root `react-native.config.js` explicitly declaring `onnxruntime-react-native`'s Android dependency config, which overrides the "has app.plugin.js, skip it" heuristic. First attempt had a bug — `sourceDir` was written relative to the *app root* (the classic RN CLI convention) but this Expo autolinking implementation joins `sourceDir` onto the *package's own directory*, so it resolved to a doubled `node_modules/node_modules/...` path and silently failed. Caught by reading `expo-modules-autolinking`'s resolver source directly rather than trusting the first rebuild's output. Verified by confirming `new ai.onnxruntime.reactnative.OnnxruntimePackage()` actually appears in the generated `PackageList.java`, and by the ONNX-dependent embeddings migration succeeding at runtime (`[db] Background re-embedding migration complete: 2/2 notes.`).

**2. Recording crash: `{ message: 'Invalid WAV file' }` from whisper.rn**
- Root cause: `services/audio/recorder.ts` used `expo-audio`'s `RecordingPresets.HIGH_QUALITY`, which records `.m4a` (AAC) on Android — a leftover from when this app used OpenAI's cloud Whisper API (which accepts AAC fine). `whisper.rn`'s README is explicit: *"Compressed formats such as MP3, AAC, and FLAC are not decoded."* Every local voice-note transcription had been silently broken since Stage 4A; it only surfaced once tested with the network genuinely off. Android's `MediaRecorder` (what `expo-audio`'s recorder uses) has no WAV/raw-PCM output option at all — an OS API limitation, not a config gap, so no preset tweak could fix this.
- Fix: rewrote `services/audio/recorder.ts` to capture raw 16-bit mono PCM directly at 16kHz via **`@fugood/react-native-audio-pcm-stream`** (verified on npm: MIT, same publisher org as `whisper.rn`/`llama.rn`, and literally the library `whisper.rn`'s own bundled realtime-transcription module is built around) and hand-assembles a WAV file from the streamed chunks (44-byte header + concatenated PCM, written in one shot — voice notes are short enough that in-memory buffering is simpler and safer than incremental disk writes). A short `STOP_DRAIN_MS` grace period after `stop()` avoids losing the tail of the recording, since the native module's `stop()` just flips a flag and its read loop exits asynchronously. `types/fugood-audio-pcm-stream.d.ts` (new) works around the package's own `.d.ts` declaring itself under its pre-rename npm name (`react-native-live-audio-stream`) rather than its actual scoped package name — the same class of fix as `whisper.rn`'s `tsconfig.json` `paths` override from Stage 4A, just via an ambient module declaration this time since the mismatch is the declared name itself, not resolution.
- `app/chat.tsx` and `app/index.tsx` needed **no changes** — both only consume `useVoiceRecorder()`'s public `{ isRecording, isTransitioning, requestPermissions, startRecording, stopRecording }` shape, which is unchanged.
- Recordings now save to `${FileSystem.documentDirectory}recordings/` instead of wherever `expo-audio` picked internally — a deliberate improvement, not just incidental: writing the file explicitly meant choosing a real persistent-storage location instead of one that risked being a cache directory subject to OS cleanup.
- `npx tsc --noEmit` clean, `npx expo export --platform android` clean (1382 modules). Native rebuild succeeded (`BUILD SUCCESSFUL in 4m 5s`) with `RNLiveAudioStreamPackage` confirmed present in the generated `PackageList.java`.

Mirrors `localWhisper.ts`'s resolution pattern — `bge-small-en-v1.5-quantized.onnx` and `bge-small-en-v1.5-vocab.txt` are resolved from `FileSystem.documentDirectory`, **not bundled** (a multi-MB model `require()`'d into the JS bundle would bloat every build; `metro.config.js` registers `.onnx`/`.ort` as asset extensions so bundling is *possible* later, but isn't what this wires up). The ONNX session is created once and memoized (resets on failure so a later call retries), same as the whisper context. Feeds `input_ids`/`attention_mask`/`token_type_ids` (standard BERT ONNX export input names — validated against `session.inputNames` at load time with a clear error if a given export uses different names, since the actual model file's exact I/O contract can't be confirmed without one in hand). Mean-pools the hidden-state output (masking padding via the attention mask — bge/sentence-transformers pooling, not `[CLS]`-only) and L2-normalizes before returning, so sqlite-vec's cosine distance behaves correctly.
- `metro.config.js` (new — didn't exist before): extends `expo/metro-config`'s default config, pushes `"onnx"` and `"ort"` onto `resolver.assetExts`.
- `db/schema.ts`: `NOTE_EMBEDDINGS_TABLE_SQL` changed from `vec0(embedding float[1536])` to `float[384])`.
- `db/client.ts`: `openDatabase()` now runs `dropStaleEmbeddingsTable()` before (re)creating `note_embeddings` — `vec0` virtual tables have no `PRAGMA table_info`-style introspection for their vector dimension, so it reads `sqlite_master.sql` for the table's original `CREATE VIRTUAL TABLE` text and regexes out `float[N]`. If `N` doesn't match `EMBEDDING_DIMENSIONS` (i.e. an old 1536-d table from before this stage), it's dropped; the table is then recreated fresh at 384-d, and `reembedAllNotesInBackground()` is fired **without being awaited** — re-embedding every note on a phone CPU could take a while, and every other `getConnection()` caller across the app is waiting on the same `openDatabase()` promise, so awaiting it here would freeze app startup. Old 1536-d vectors are dropped wholesale rather than converted (there's no way to project a 1536-d OpenAI embedding into 384-d bge-space); failures on individual notes during re-embedding are logged and skipped rather than aborting the whole pass.
- `services/notes/noteManager.ts`: `createVoiceNote`, `createTextNote`, and `hybridSearchNotes`'s query-vector generation all switched from `generateEmbedding` (OpenAI) to `generateEmbeddingLocal`. (The task brief described this as a `services/ai/rag.ts` change, but `rag.ts` only calls `hybridSearchNotes` — it never generates embeddings itself; the actual query-embedding call lives inside `hybridSearchNotes` in `noteManager.ts`, which is what was changed.) The old `services/ai/embeddings.ts` (OpenAI) is left in place, now fully unreferenced — same treatment as Stage 4A's leftover `services/ai/whisper.ts`.
- `npx tsc --noEmit` — clean, zero errors. `npx expo export --platform android` — bundles clean (1377 modules, up from 1353).
- **Native rebuild required before on-device testing**: `onnxruntime-react-native` ships native `android`/`ios` folders — needs `npx expo prebuild --clean` + rebuild, same as `whisper.rn` before it. **Both the ONNX model and its vocab file need to be manually pushed** to the app's document directory before embeddings can be generated at all — there's no in-app download/picker for either yet.

**Phase 4 Stage 4A — On-Device Local Whisper Transcription**
- The task brief named `react-native-whisper` for this; checked it on npm first — it's a single-version (`0.0.1`), year-stale package from a lone maintainer, not a real whisper.cpp binding. Used **`whisper.rn`** (`0.7.2`) instead, the actively maintained RN binding for whisper.cpp.
- `services/ai/localWhisper.ts` (new): wraps `initWhisper`/`WhisperContext.transcribe` from whisper.rn. `resolveModelPath()` looks for `ggml-base.en.bin` then `ggml-tiny.en.bin` in `FileSystem.documentDirectory` — models are **not bundled** into the app (too large); a model file has to be placed there manually or by a future download step before transcription works. The whisper context is created once (`getWhisperContext()`, memoized promise, resets on failure so a later call can retry) and reused across calls. `transcribeAudioLocal(fileUri)` returns raw transcript text; callers (unchanged) still run it through `isSilentTranscript()` themselves — pulling that import into `localWhisper.ts` directly would create a cycle (`noteManager` → `localWhisper` → `noteManager`).
- `services/notes/noteManager.ts` and `app/chat.tsx`'s voice-query handler both now call `transcribeAudioLocal` instead of `services/ai/whisper.ts`'s OpenAI-backed `transcribeAudio` — voice transcription (notes and chat) no longer needs a network round-trip or `OPENAI_API_KEY`. The old `services/ai/whisper.ts` (OpenAI API) is left in place, unused by these two call sites, in case something else still wants server-side transcription.
- **Packaging quirk worth knowing about**: `whisper.rn@0.7.2`'s `package.json` `exports` map has no root `"."` entry, only `"./*"` subpath patterns — `import ... from "whisper.rn"` fails under strict exports resolution (confirmed via plain `node -e "require('whisper.rn')"` → `ERR_PACKAGE_PATH_NOT_EXPORTED`; every published version back to 0.5.5 has the same gap). Worked around by importing `whisper.rn/index` instead, which matches the `"./*"` pattern. That still didn't fully fix `tsc`, because the pattern's condition order (`react-native` before `types`) means bundler-mode resolution type-checks the raw, untranspiled `src/index.ts` (which assumes RN's ambient `global` and fails standalone `tsc`) instead of the prebuilt `.d.ts`. Fixed with a `tsconfig.json` `paths` override redirecting only *type-checking* of `whisper.rn/index` to `node_modules/whisper.rn/lib/typescript/index.d.ts`; Metro still resolves the same specifier to `src/index.ts` at runtime and transpiles it normally.
- `safe-buffer` (a whisper.rn dependency) requires Node's `buffer` module, which Metro doesn't polyfill by default — `npx expo install buffer` (RN-standard polyfill package) resolved a bundling failure (`Unable to resolve module buffer`).
- `npx tsc --noEmit` — clean, zero errors. `npx expo export --platform android` — bundles clean (1353 modules, up from 1346).
- **Native rebuild required before on-device testing**: `whisper.rn` ships `android`/`ios` native folders (like `op-sqlite`'s FTS5 flag and `expo-speech` before it) — `npx expo prebuild --clean` + rebuild is required before `initWhisper`/`transcribe` will actually work on-device; `tsc`/`expo export` only validate JS/bundling, not native linkage. A GGML model file (`ggml-base.en.bin` or `ggml-tiny.en.bin`) also has to be manually pushed to the app's document directory on the emulator/device before transcription can succeed — there's no in-app model download/picker yet.


**Phase 3C — Rich Note Detail & Audio Playback Subsystem**
- `services/audio/player.ts`: single-instance audio player singleton built on `expo-audio`'s `createAudioPlayer`. Exactly one native `AudioPlayer` exists app-wide; starting a new track always pauses/replaces whatever was previously playing. Exposes state via `useSyncExternalStore` through `useAudioPlayerControls(uri)`, reference-counts mounted consumers, and releases the native player once the last one unmounts. Missing/inaccessible files and native failures are caught and surfaced as `state.error`, never thrown.

- `components/NoteDetailModal.tsx`: bottom slide-up sheet (`noteId`, `visible`, `onClose`, `onDeleted`). Fetches the full note itself via `getNoteById` (works uniformly whether the caller has full note data or just a partial RAG citation). Shows transcript, formatted timestamp, status badge (no topic/tag extraction exists in the schema — status substitutes for "metadata"), embedded audio controls, and an atomic delete that pauses playback → `deleteNote` → closes → notifies parent.
- Wired into both `app/index.tsx` (tap a note card to open the modal; inline compact playback directly on cards, including search results) and `app/chat.tsx` (tapping a `[Note N]` citation chip opens the same modal instead of a plain `Alert`).

**Phase 3D Stage 1 — Voice Query Input in Chat**
- `app/chat.tsx` gained a mic button in the input bar using the existing `services/audio/recorder.ts` (`useVoiceRecorder`) and `services/ai/whisper.ts` (`transcribeAudio`).
- States: `isRecordingVoice` (derived directly from `recorder.isRecording`, not duplicated), `isTranscribingVoice`, `recordingDuration` (ticked by a 1s interval while recording).
- Recording → stop → transcribe → auto-submit via a refactored `handleSend(overrideText?: string)`. Voice submissions don't clobber whatever the user had separately typed into the input box.
- Silence detection reuses `isSilentTranscript()`, newly exported from `services/notes/noteManager.ts` (was a private regex used only for voice notes) — both the note-recording flow and the chat voice-query flow now agree on what counts as "Whisper heard nothing" instead of drifting independently.
- Lifecycle safety: a `useFocusEffect` cleanup (via a `recorderRef` to avoid re-running on every render, since `useVoiceRecorder()` returns a new object each render) stops any in-progress recording if the user navigates away from the Chat tab mid-recording.

**Phase 3D Stage 2 — Hands-Free Text-to-Speech Output**
- `expo-speech` installed (native module — has `android`/`ios` folders, so like `op-sqlite`'s FTS5 flag earlier, it requires a native rebuild — `npx expo prebuild --clean` + rebuild, or a fresh dev-client build — before `Speech.speak()` actually works on-device; `tsc`/`expo export` only validate JS/bundling, not native linkage).
- `services/audio/tts.ts` (new): `sanitizeTextForSpeech(text)` strips fenced/inline code, `[Note N]` citation chips, markdown headers, and bold/italic markers before narration. `speakText(text, options?)` sanitizes then always calls `stopSpeech()` first — same single-instance principle as `services/audio/player.ts`, so TTS utterances can never overlap each other. `stopSpeech()` wraps `Speech.stop()` and is safe to call when nothing is speaking.
- **Audio focus management (single active audio source, app-wide)**: `services/audio/player.ts`'s `playUri()` now calls `stopSpeech()` before loading any note recording, so tapping play on a note interrupts TTS narration. `app/chat.tsx` calls `stopSpeech()` before starting a new voice recording and before sending any new message (text or voice) — a new question always interrupts the assistant reading a previous answer.

Each assistant bubble gets a "🔊 Listen" / "⏹ Stop" toggle button.
- Lifecycle safety: extended the *existing* recording-cleanup `useFocusEffect` (rather than adding a second, redundant effect) to also call `stopSpeech()` on blur/unmount, so navigating away from Chat stops narration immediately — this gives Silent Confidant genuine hands-free/driving-mode capability: ask by voice, get an answer read aloud, with playback correctly yielding to notes/recording/new questions and cutting off the instant you leave the screen.

## Architecture Integrity

- `npx tsc --noEmit` — clean, zero errors, verified after every increment across this whole project.
- `npx expo export --platform android` — bundles clean (1346 modules as of this commit).
- **Hybrid note search**: `hybridSearchNotes()` in `services/notes/noteManager.ts` fuses sqlite-vec cosine-distance ranking with FTS5 keyword ranking via reciprocal rank fusion, filtered to `status = 'embedded'` and Whisper-noise-filtered. This is the *only* search path now — the old vector-only `searchNotes()` was removed; both the Notes tab search bar and RAG chat retrieval go through the same function.
- **Native op-sqlite/FTS5**: `db/client.ts` degrades gracefully (`isFtsAvailable()`) if the linked native build wasn't compiled with FTS5 (`op-sqlite.fts5: true` in `package.json` requires a native rebuild — `npx expo prebuild --clean` + rebuild — to take effect, not just a JS/Metro change). `note_embeddings` (sqlite-vec) has no explicit primary key and relies on `rowid`, joined against `notes.rowid`; `notes_fts` is an FTS5 external-content table kept in sync by triggers using the special `('delete', ...)` command (a plain `DELETE`/`UPDATE` trigger doesn't work correctly against external-content FTS5 tables).
- **Known environment quirk**: this dev machine's only JDK (25, JetBrains Runtime) is too new for the current Android Gradle Plugin's native CMake step. A working JDK 17 was already auto-provisioned by Gradle at `~/.gradle/jdks/eclipse_adoptium-17-amd64-windows.2` — point `JAVA_HOME` at it for any future native (`gradlew`) build rather than the system default.
- **Known environment quirk**: `npm install` for any package with a native-artifact-download postinstall step that shells out to `tar` (e.g. `llama.rn`) must be run through the PowerShell tool, not Bash — Bash on this machine is Git Bash/MSYS, whose `tar` doesn't understand Windows drive letters and misparses `C:\...` paths as a remote `host:path` spec.
- Vestigial `entities`/`relationships` schema and the Drizzle ORM dependency were both real technical debt identified in an earlier audit; the unused tables were removed, but `drizzle-orm`/`drizzle-kit` are still installed (only referenced by `db/client.ts`'s unused `getDatabase()` accessor) — safe to remove later, not yet done.
