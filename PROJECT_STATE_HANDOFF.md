## Fine-tuning workstream — Hybrid Extraction Architecture

**Status: wired into the app and shipping in production 1.0.37 (Build 48).** The pre-filter has been live since it was written (model-agnostic, ran regardless of which model was active); the fine-tuned GGUF itself, and the prompt-mode default flip, were wired in via commit `47cc7a7` (`services/ai/localLlama.ts`'s `CHAT_MODEL` now points at `qwen-task-extractor-q4_k_m.gguf`, `extractionPromptMode`/`ragPromptMode` now default to `"minimal"`) and verified on-device via adb/logcat: retired-model cleanup fired, the new GGUF registered with and completed through Android's native DownloadManager at the correct byte count, cold model load succeeded, minimal-mode prompts were confirmed active (71/80-token cache sizes, not just assumed), the pre-filter fired correctly against live notes, and an existing anchoring guard caught a real model hallucination during testing. This section's numbers below (94.2%, the six-attempt table) describe the offline eval-harness result that justified shipping it, not a claim about on-device accuracy specifically — no on-device accuracy re-score against the 103-case corpus has been run, only functional/pipeline verification.

**The problem:** a prompt-only baseline (83.5%, 86/103) had two failures three rounds of prompt engineering couldn't move — third-party attribution (0/8) and pure-observation refusal (the model inventing tasks from purely descriptive notes). Six real training attempts followed:

| Attempt | Approach | Result |
|---|---|---|
| v1 | Plain SFT, extraction only | Fixed both targets but broke dates/recurrence/STT/RAG — worse overall (70.9%) |
| v2 | Plain SFT, 50% refusal | Fixed third-party/refusal, broke dates/recurrence |
| v3 | Plain SFT, 15% refusal + contrastive pairing | Fixed dates/recurrence, broke third-party/refusal again — same seesaw, opposite direction |
| v5-v7 | ORPO (preference pairs), escalating third-party volume/capacity each round | v7 (LoRA r=32, 3 epochs, 70 third-party rows) scored 68.9% — WORSE than the baseline. Its actual failures were near-verbatim reproductions of its own `rejected` fabrication strings ("Have the plumber come", "Move house") — proof the model had memorised a small fixed vocabulary of wrong answers rather than learned the general rule |
| **Hybrid + v8.1** | Deterministic code pre-filter for third-party/refusal + SFT (not ORPO) scoped to what every prior run got right | **94.2% (97/103)** |

**The fix, in two parts:**

1. **`preFilterZeroTaskNotes`** (`services/ai/extractionLogic.ts`) — a regex-based, deterministic pre-filter that short-circuits extraction to `[]` for third-party/observation notes, without calling the LLM at all. Verified against the frozen 103-case corpus with **zero false positives** before being written (gated on `isSingleSentence` so it can never fire on a contrastive note that also contains a real task). Wired into `transformationEngine.ts`'s real extraction path and `scripts/eval/runEval.ts`'s harness. Tested alone against the still-broken v7 checkpoint (zero retraining): **87.4%** — most of the total win is this guard, not the fine-tune.
2. **Dataset v8.1** (`scripts/dataset/generate_sft.py`, standard SFT `messages` format, not ORPO) — 500 rows: 270 positive + 80 contrastive extraction (zero refusal examples — that's the pre-filter's job now), 125 RAG-factual + 25 RAG-refusal. Trained via `notebooks/qwen_sft_unsloth.ipynb` (Unsloth `SFTTrainer` + `train_on_responses_only`, lr=8e-5, 2 epochs, LoRA r=16) into `qwen-task-extractor-q4_k_m.gguf`.

**What's actually deployed:** both halves now. The pre-filter has been live in `transformationEngine.ts` since it was written (model-agnostic, fires regardless of which model runs). The fine-tuned GGUF is uploaded to the `xayra-models` R2 bucket, `services/ai/localLlama.ts`'s `CHAT_MODEL` points at it, `modelDownloadManager.ts` is wired to fetch it, and `extractionPromptMode`/`ragPromptMode` both default to `"minimal"` (the fine-tuned model's ~212-token prompt, not the ~2,478-token stock-model prompt). All of it is verified on-device (see the status line above) and shipping in production 1.0.37.

**Known residual gap:** `rag-grounding` still misses 2/4 on indirect multi-note questions ("Do I need to do anything about the gym?", asked against a gym-renewal note buried among distractors) — the v8.1 dataset additions aimed at this (new `gym` indirect phrasings, new `recommendation_book`/`dietary_note` RAG subjects) fixed 1 of 3 targeted cases (`rag-005`). Worth another pass if resuming RAG work specifically.

### 1. Handsfree wake-word feedback (chime + logo glow)

A real feasibility investigation into a true "listens live" acoustic wake-word engine (two-stage partial transcription, Picovoice Porcupine, openWakeWord, and a proposed Android-native-hotword hook) was carried out and **closed without a change**: Porcupine needs a paid commercial license (contradicts CLAUDE.md's zero-cloud-API-dependency rule for the core loop), openWakeWord has no pre-trained "Hey Xayra" model and would need a from-scratch mic-capture→spectrogram→ONNX pipeline, and Android's native hotword APIs (`CAPTURE_AUDIO_HOTWORD`) have been `signature|system`-protection-level and unreachable by any Play Store app since Android 12 — confirmed a hard platform wall, not a workaround-able gap. Decision: keep the existing transcript-based detection (`containsWakeWord()` in `services/audio/activeMode.ts`, fires only after the full utterance is VAD-segmented and Whisper-transcribed) and add feedback at the moment it fires, rather than pretending it's live.

The `.wav` asset is synthesized locally by `scripts/generate-wake-chime.js` (hand-written WAV header + PCM sine tones) rather than sourced, avoiding licensing questions. Preloaded when Handsfree mode starts, released when it stops.
- **`components/CentralRecorderCanvas.tsx`** — new `"listening"` canvas state driving a breathing accent-colored glow halo around the record button (Reanimated `withRepeat`/`withTiming`). Required wrapping the button in a new sized `buttonStack` container so the oversized glow overlay has a positioning context to center against — the original flat layout couldn't host it.
- `app/index.tsx` plays the chime immediately when a Handsfree wake-word match fires.

## Build 47 — Single-Model Cutover: Qwen2.5-1.5B-Instruct

**Origin**: v1.0.35 (versionCode 42) was tested on a Pixel 9 via Play Store internal testing and judged not production-ready on two counts — a ~15s cold first retrieval, and Handsfree wake-word detection missing roughly half the time in ambient road noise. The directive was a strict cutover to one permanent engine with no fallback sequence beneath it.

### 1. One model, no tier ladder

`LLAMA_MODEL_FILENAMES` (a priority-ordered list) is replaced by a single `CHAT_MODEL` constant in `services/ai/localLlama.ts`:

```
qwen2.5-1.5b-instruct-q4_k_m.gguf   —   1,117,320,736 bytes   —   label "Qwen2.5-1.5B"
```

**Deleted outright**, not deprecated: `attemptTierUpgrade()`, `maybeAttemptTierUpgrade()`, `TIER_1B`/`TIER_3B`, the `LlamaTier` type, `resolveDefaultLlamaTier()`/`resolveActiveLlamaTier()`, and the `tier3BStatus` preference. The 1B→3B ladder existed because device capability couldn't be predicted up front; with one model sized to run everywhere there is nothing left to choose between. `RAM_FLOOR_FOR_3B_BYTES` survives, renamed to `RAM_FLOOR_FOR_TRIALS_BYTES` — thread escalation still uses it as a "has headroom to spare" proxy.

`resolveModelPath()` now resolves exactly one filename and throws `LLAMA_MODEL_MISSING_ERROR_PREFIX` otherwise. That throw is a **missing-asset path, not a fallback**: `app/chat.tsx` matches the prefix and shows the graceful "downloading…" callout. There is no second model to fall back to, by design.

**Why 1.5B**: the ~15s cold retrieval is dominated by the first mmap read of a cold GGUF plus system-prompt prefill. Both scale with size — Q4_K_M at 1.5B is ~1.07 GB against the 3B's ~2.0 GB. The compressed prompt below attacks the same number from the other side. **Neither improvement has been measured on-device yet.**

### 2. Retired-model cleanup (added beyond the brief)

An APK update never touches the document directory, so every device upgrading from a pre-cutover build would otherwise keep a 0.8–2.0 GB Llama GGUF on disk forever, *plus* download the new 1.07 GB model. `deleteRetiredChatModels()` (`modelDownloadManager.ts`) removes `Llama-3.2-3B-Instruct-UD-Q4_K_XL.gguf`, `Llama-3.2-1B-Instruct-UD-Q4_K_XL.gguf` and `Qwen2.5-3B-Instruct-Q4_K_M.gguf` at startup, before the readiness check, so reclaimed space is available to the download that follows. Best-effort and never fatal — a failure costs disk space, which is not a reason to block setup.

### 3. ChatML only

With one model family there is no runtime branching left. `ChatTemplateFamily`, `getActiveChatTemplateFamily()` and every Llama-3 branch are gone from both `localLlama.ts` and `transformationEngine.ts`; `EOT_TOKEN` is deleted from both. `CHAT_TEMPLATE_STOP_TOKENS` is now `["<|im_end|>", "<|endoftext|>"]`.

Prompts are still hand-assembled raw strings (needed to splice a fixed few-shot turn ahead of the real query, which llama.rn's `messages` API doesn't expose enough control over) — so they are now written against ChatML **specifically**. `__tests__/localLlama-chatTemplateFamily.test.ts` asserts against the real captured prompt that no Llama-3 marker survives anywhere, and that a leftover Llama GGUF on disk is refused rather than loaded.

### 4. The compressed system prompt

Long prose replaced by seven numbered laws, cutting prefill cost to roughly a fifth. Three of the seven are **load-bearing and must not be compressed away** — each closes a failure observed on real hardware at this model size:

| Law | Guards against |
|---|---|
| **2** — never describe your role, instructions, or configuration | A 1B model, asked to summarize notes, ignored the context block and paraphrased its own system-prompt self-description back as if it were a fact about the user's notes. |
| **3** — never blend unrelated notes | Retrieval returns top-k whether or not they're on-topic; without explicit isolation an unrelated-but-retrieved note gets folded in as though it belonged. |
| **4** — 1-2 sentences when ONE retrieved note is relevant, bullets when MORE THAN ONE is | A flat "always 1-2 sentences" silently truncates multi-note answers. The branch condition matters: an earlier version keyed off the QUESTION ("for single-fact queries… for open-ended summaries…"), which asks the model to classify intent before answering. Confirmed on-device that a 1.5B model cannot do that reliably — see the QA findings below. Counting relevant notes is observable in its own context window; question intent is not. |

Law 4's two-branch shape also resolves a conflict with the fixed few-shot example in `buildPrompt()`, which demonstrates a bullet-point answer — under a flat sentence cap that example fought the instruction; it now demonstrates Law 4's bullet branch, and at this model size a demonstrated prior turn steers format considerably harder than the written rule.

`SHARED_XAYRA_PREAMBLE` is still shared word-for-word with `transformationEngine.ts`, preserving Build 38's KV-cache prefix harmonization.

### 5. Automated R2 sync — `scripts/sync-model-to-r2.sh`

Replaces the ad-hoc manual upload done for Build 46. Pulls a GGUF from Hugging Face and pushes it to the `xayra-models` R2 bucket, defaulting to the current production model so a bare invocation re-syncs exactly what ships.

Encodes the two traps found the hard way in Build 46: `wrangler r2 object put` silently writes to a **local** `.wrangler/` cache without `--remote`, and hard-fails above **300 MiB** with it. The script uses `aws s3 cp` against R2's S3-compatible endpoint (`https://<account_id>.r2.cloudflarestorage.com`), which handles multipart transparently. It also verifies **GGUF magic bytes before upload** — guarding the failure where a 404 HTML page lands on disk under a `.gguf` name and only surfaces much later inside `initLlama()` — and confirms the Worker actually serves the object afterwards, since "the bucket accepted it" and "the app can download it" are different claims.

**Live and verified** at `https://xayra-models-proxy.vermagauravsingh.workers.dev/qwen2.5-1.5b-instruct-q4_k_m.gguf`: HTTP 206 on a range request (Android `DownloadManager` resumes via range requests, so this specifically matters), first four served bytes are `GGUF`, full GET returns exactly 1,117,320,736 bytes.

### 6. Wake word — carrier-word corroboration (text layer only)

**What was asked for**: standardize on a higher-density trigger phrase ("Hey Xayra") and replace text matching with a real acoustic wake-word engine.

**What shipped**: the phrase standardization, implemented as an *optional* carrier rather than a requirement. Requiring "Hey" before "Xayra" in the transcript would have made the miss rate **worse** — `activeMode.ts` documents, confirmed via on-device logcat, that the first word of an utterance is the one most likely to be dropped during native audio cold-start, so mandating a carrier adds a second token that must survive exactly where transcription is weakest. Instead the carrier acts as corroboration: when one of `hey / hi / ok / okay / listen / yo` immediately precedes it, the wake token gets a looser fuzzy budget (edit distance 3 vs 2), because "hey <something-xayra-shaped>" is far less likely to be coincidence than a bare five-letter token. Bare "Xayra" still works unchanged. `WAKE_PHRASE_DISPLAY` keeps the UI prompt and the matcher from drifting apart.

**What did NOT ship — the acoustic engine.** Both candidates have real external blockers:
- **Picovoice Porcupine** requires a paid commercial license and an AccessKey for production use, which directly contradicts CLAUDE.md's *"Zero-cloud-API dependency for the core loop… must never require a network call or an API key."* Handsfree is core loop. This is a product/licensing decision, not an implementation one.
- **openWakeWord** is Apache-2.0 and would ride on the already-integrated `onnxruntime-react-native` — the better fit — but **no pre-trained "Hey Xayra" model exists**; it requires training via their synthetic-TTS pipeline (hours of GPU time). That is a model-training workstream, not a code change.

Either path additionally needs concurrent raw-PCM access alongside the existing capture session (a native change). `activeMode.ts:87-99` has stated this constraint since Build 24; it remains accurate. **The ~50% miss rate in road noise is therefore mitigated, not solved.**

### 7. Prompt-session cache (`saveSession`/`loadSession`)

Added after the on-device measurements below showed prefill — not model load — was the dominant cost in the reported ~15s cold retrieval.

llama.cpp's KV state for the static prompt prefix is persisted to disk and restored into each fresh context, so the prefix is evaluated once rather than on every cold start and every reload after the background release.

- **Restore lives in `loadContext()`**, not in the warm-up, so every fresh context benefits — including the post-background reload, which is the common case in real use. Skipped for thread-escalation trials, which measure decode against a throwaway prompt sharing no prefix.
- **Invalidation hashes the fully-built warm-up prompt.** `buildSystemPromptWithDate()` bakes today's date and the Monday-to-today baseline into that text, so the key changes at local midnight with no separate date field. A session restored the next morning would otherwise leave the model resolving "yesterday" and "this week" against a stale baseline — silently, with no error. Model filename and `n_ctx` are in the key too, since a session is only valid for the exact model that produced it.
- **Every failure path is non-fatal**: missing, stale, corrupt or model-mismatched all degrade to paying the prefill once, which is the pre-cache behaviour. A session that fails to load is discarded *and replaced*, so a bad file is never retried every launch.
- **`saveSession` does not strip a `file://` prefix** the way `loadSession` does — it must be given a bare filesystem path, or it writes somewhere that never loads back.
- The background release now also re-arms the memoized warm-up. Without that, sitting backgrounded across midnight would discard the stale session with nothing left to write a fresh one.

### Measured on-device (Redmi Note 8 Pro, 2-thread inference)

All figures from the dev build of 1.0.36/versionCode 43, models freshly downloaded from R2.

| Metric | Value | Notes |
|---|---|---|
| Llama cold model load | **11.4 s** first-ever read; **4.8–6.7 s** warm | Qwen2.5-3B measured 21.6 s on this same device in Build 46 — the ~47% drop tracks the file-size ratio (1.07 GB vs 2.1 GB), consistent with load being I/O-bound. |
| Static prompt prefill (556 tokens) | **~14.0 s** | The cost the session cache removes. Measured as the gap between model load completing and the session save starting, so it includes queue scheduling. |
| Prompt-session restore | **18 ms** | Replaces the ~14 s above. |
| Prompt-session save | 45–52 ms | Written once per invalidation key, not per launch. |
| Session file size | 15.95 MB for 556 tokens | 28.7 KB/token, matching the architecture estimate (28 layers × 2 KV heads × 128 head_dim). |
| Native heap, model resident | **1.98 GB** (2.4 GB total PSS) | |
| Native heap, after background release | **0.51 GB** (0.83 GB total PSS) | The release reclaims ~1.5 GB. |

**Why the background release was kept.** The cutover to a 1.07 GB model did *not* reduce the footprint proportionally — a resident context still costs ~2 GB once the KV cache at `n_ctx: 4096`, llama.cpp's compute buffers and the Whisper context are counted alongside the weights. That is at or above the 1.75 GB that motivated the Build 41 release, so holding it while backgrounded remains exactly the profile Android's low-memory killer reaps. The session cache does not replace that release — it removes its cost.

**The ~14 s prefill figure is close to the originally-reported ~15 s Pixel 9 cold retrieval**, which suggests prefill was essentially the whole of that symptom. On that reading the session cache, rather than the model swap, is the change that addresses the complaint that started Build 47.

### 8. Dual prompt-session cache (both prefixes, not just RAG)

RAG answers and to-do extraction share one llama context and do NOT share a prefix. Each evicted the other's KV state, so alternating between asking and saving — ordinary use — paid a full re-prefill every time. Only RAG had a disk cache, so extraction paid worst.

Session files are now namespaced per prefix (`llama-prompt-session-rag.*`, `llama-prompt-session-extraction.*`), the completion queue tracks which prefix is resident, and a job whose prefix differs restores its own copy first.

Two implementation notes worth keeping:

- **The save must be awaited inside the queue's exclusive slot.** Fired as `void` it raced the next job for the context and failed on-device with `"Context is busy"`, and with `"Context not found"` when the background handler released the context underneath it.
- **`residentPrefixKind` resets on release**, since the KV cache dies with the context; a stale value would skip the restore and silently re-prefill.

A related fix in `transformationEngine.ts` was a precondition for this paying off: the per-note detected-phrases block used to sit near the TOP of the extraction system prompt, ahead of ~2,000 tokens of rules and fourteen few-shot turns. Cache reuse stops at the first differing token, so that placement capped reuse at a few hundred tokens. Moving it into the user turn made the whole static opening byte-identical between notes.

**Measured on-device (Redmi Note 8 Pro), all swaps confirmed in both directions and across a process restart:**

| Scenario | Before | After |
|---|---|---|
| Boot → first RAG | ~14s prefill | 42ms restore |
| Cold process → first extraction | 77s | **8.2s** |
| After a RAG query → extraction | 77s | 8.6s |
| After an extraction → RAG (TTFT) | 54s | **2.0–3.4s** |
| Swap cost, either direction | — | 18–136ms |

Session file sizes: **16 MB** (rag), **64 MB** (extraction). The extraction file is large because its prefix is; it grows with the prompt, which is a real cost of this approach and an argument for shortening the prompt rather than only caching it.

**Full cold-start cycle** (force-stopped process → voice note → extraction → spoken question → answer):

| Step | Time |
|---|---|
| Note saved → to-do created | 12.4s |
| Question STT (Whisper) | 4.9s |
| Retrieval | 28ms |
| TTFT | 1.97s |
| Full answer | 5.1s |

**Memory through that same cycle — watch this:**

| Point | Native heap | Total PSS |
|---|---|---|
| Cold idle (model loaded, RAG restored) | 1.47 GB | 1.72 GB |
| After voice note + extraction | 1.87 GB | 3.01 GB |
| After the question was answered | 1.89 GB | 3.04 GB |

The ~1.3 GB jump from idle to post-extraction is **not explained**. Whisper's model is only ~150 MB, so it does not account for the gap. Thread count is not a plausible cause (threads add scratch buffers in MB, not GB). Nor is this device's RAM management: the app's own footprint should travel to a Pixel 9 largely unchanged — what differs is headroom, and 3 GB resident is comfortable on 12 GB and not on 6 GB. Build 40's onboarding kills came from exactly this pressure. Worth investigating before assuming it is fine.

### QA against a realistic corpus

`app/dev-seed.tsx` (dev-only, `xayra://dev-seed`) seeds 12 notes spanning 25 days, chosen to exercise specific guardrails rather than to look plausible. It must go through `createTextNote()` rather than raw INSERTs — that is what generates each note's embedding, and a directly-inserted row is invisible to vector search.

**Findings from the first pass (Qwen2.5-1.5B, Redmi):**

- **Grounding holds under temptation.** Asked about renewing a passport — nothing in the corpus — retrieval still placed the *car registration* note in context (distance 0.389, inside the floor, because "renewing" matches "renew"). The model refused anyway rather than answering from it. Law 1 passed where it actually counts, not just on an empty context.
- **The refusal wording drifts** ("There is no note about renewing your passport" instead of the mandated line). No functional impact — **nothing in the codebase depends on that exact string**; it appears only in the prompt and one comment. Cosmetic, not load-bearing.
- **Law 4's branch condition was wrong, and the corpus caught it.** Asked "what do I need to sort out for Anita's dinner?", with BOTH relevant notes retrieved and inside the relevance floor (booking 0.297, allergy 0.283), the model answered with only the allergy — silently dropping the actionable half. Retrieval was correct; synthesis failed. Root cause was Law 4 asking the model to classify the question's intent. Rewritten to key off how many retrieved notes are relevant; re-tested, it now returns both as bullets, and a genuine single-note question ("when does my car registration expire?") still answers in one plain sentence rather than over-correcting into bullets.
- **Law 3 (no blending) has not really been tested yet.** It passed, but the relevance floor excluded 10 of 12 notes before the model saw them — that is retrieval discipline, not demonstrated model discipline. A real test needs two genuinely similar notes both clearing the floor.
- **Date mechanics confirmed end-to-end**: "Renew car registration" → 2026-09-30, "Book a table for six" → 2026-09-19 19:00.

**Caveat on the device**: the Redmi is the CPU-starved 2019 device capped at 2 inference threads. It is a sound proxy for correctness and grounding, and a poor one for Pixel 9 latency.

## Build 46 — Qwen2.5-3B-Instruct Model Trial *(superseded by Build 47 above)*

**Origin**: the user asked for a similarly-sized-or-lighter, license-clean, more nuanced local LLM alternative to Llama 3.2 3B, specifically one that handles multi-turn follow-ups well. Recommended **Qwen2.5-1.5B-Instruct** (Apache 2.0, ~1GB, 32K context) as the best fit for "lighter AND still capable," with Qwen2.5-3B-Instruct and Gemma-2-2B-it presented as alternatives (Gemma flagged for its 8K context ceiling — later found moot, since this app hard-caps `n_ctx` at 4096 regardless of model). The user chose to try **Qwen2.5-3B-Instruct** instead — same size class as the current model, better published benchmarks and a cleaner license (Apache 2.0 vs. Meta's Llama license) than Llama 3.2, not the "lighter" pick but a reasonable one given they wanted to trial the swap on the same footing first.

## Build 44 — Live Bug Fixes: Drive Backup Data-Loss Guard, Handsfree Persisting Across Navigation

**Origin**: two bugs reported directly by the user from real device testing, outside the 3-phase QA stabilization process (Builds 41-43) — triaged and fixed the same session, given bug 1's severity.

**Bug 1 — Drive backup could silently destroy an existing backup (data loss, fixed).** Reported scenario: the user uninstalled the dev build from their Pixel 9 and installed the Play Store tester build — a different app identity with a genuinely empty local database. They then reached for the wrong one of Settings' two Cloud Backup buttons ("Back Up Now" vs. "Restore / Sync Notes") and, by their own account, backed up while local notes were at zero; when they then tried to restore, Drive had nothing left to give back.

**Root cause, confirmed by reading the actual code, not guessed**: `backupToDrive()` (`services/sync/driveSync.ts`) had zero awareness of what already existed in Drive — it unconditionally `VACUUM INTO`s whatever is in the *local* database right now and overwrites the remote `remi_backup.db`/`remi_backup.key` files with it, no matter how empty that local database is or how much real data the remote backup already held. `restoreFromDrive()` itself was never at fault — it's a safe, additive, merge-only read from Drive that can never delete or overwrite anything; the only genuinely destructive operation in this file was the backup path.

**Investigated the user's follow-up question — "was backup ever delta before, and did something regress?"** — by reading this file's actual git history at three points (its original introduction, the commit at versionCode 15 specifically, and today), plus this project's own contemporaneous documentation from when Drive sync was first built. All three agree: `backupToDrive()` has been a wholesale `VACUUM INTO` overwrite since the feature's very first commit — it was never delta, and nothing regressed. Only `restoreFromDrive()` has ever been delta. The bug was latent the entire time; it just never had a visible failure mode until the exact "0 local notes, real backup already exists" combination occurred (a fresh reinstall), which is very likely the first time that specific condition was ever hit in testing.

**Fix — a true delta backup, per the user's explicit redesign request, superseding an earlier confirm-before-overwrite version of this fix**: `backupToDrive()` now checks whether a remote backup already exists. If not (a genuinely fresh account), it uploads a plain local snapshot as before — there's nothing to merge with. If one **does** exist, it downloads it, opens it writable, and `INSERT OR IGNORE`s whichever local notes/to-dos aren't already in it by id (the exact mirror-image of `restoreFromDrive()`'s own `mergeMissingNotes`/`mergeMissingToDos` merge, just in the opposite direction) — then re-uploads that merged result. New `listAllToDos()` export added to `todoManager.ts` (every to-do regardless of completion status, unlike the existing `getPendingToDos()`) to source the to-do half of this. The merge step is INSERT-only — it can only ever add rows to the downloaded copy, never remove or replace any — so 2 new local notes against 15 already in Drive correctly become 17, and 0 local notes against 15 in Drive correctly leaves all 15 untouched, structurally rather than by a confirmation dialog. The remote backup's own encryption key never needs to change on a merge — the downloaded copy is opened and written to using the exact key it already has. Locked in with `__tests__/driveSync-deltaBackup.test.ts` (3 tests, including the exact "0 local vs. 15 in Drive" scenario from the live incident, asserting all 15 remain).

**Data recovery for the user's actual lost notes**: flagged separately as time-sensitive — Google Drive keeps a rolling revision history for uploaded file content (including `appDataFolder` files), so the *pre-overwrite* version of `remi_backup.db`/`remi_backup.key` may still be recoverable via the Drive Revisions API even though the "current" version is now empty, if this hasn't aged out of Drive's retention window. Not yet built — a real decision for the user on whether it's worth the effort for what was on that device, discussed but deferred pending their answer.

**Bug 2 — Handsfree mode turning off on navigation (fixed).** Reported: engaging Handsfree, then navigating to Archive or Settings, silently turned it back off with no feedback — unwanted, since Handsfree is meant to be an ongoing, hands-free mode that doesn't require staying on the Home screen. Root cause: Build 42's P3-b fix (`app/index.tsx`) added a `useFocusEffect` blur-cleanup that stopped *both* a plain manual recording and Handsfree whenever the Home screen lost focus (i.e., any navigation away) — reasonable for a manual recording (a short, actively-watched foreground action), wrong for Handsfree (checked directly: `TodosOverlay`, the To-Dos overlay, is a plain sibling `<View>` rendered conditionally inside `app/index.tsx` itself, not a real navigation, so it was never actually affected by this — only Archive and Settings, both real `router.push` navigations, ever were).

**Fix**: removed Handsfree's stop-on-blur call entirely, keeping only the manual-recording stop. The one case that still correctly turns Handsfree off is leaving the *app* entirely (`useActiveMode()`'s own `AppState` listener, Build 42's P2-3 fix) — untouched by this change. No automated regression test — this is component-level navigation behavior and RNTL remains confirmed non-functional in this stack (same honest gap as Build 43's P3-1); verified by code reading of the exact focus-effect mechanism, not yet re-confirmed live on-device.

## Build 40 — Three-Layer Onboarding Memory-Pressure Defense, Splash-Screen Root Cause, Greeting Copy Fix

**Origin**: real production bug reports from Build 39's Play Store internal test on a Pixel 9, forwarded with screenshots. Rather than patch symptoms blind, the user explicitly authorized ("Do it") building and installing a fresh **development-client** build so the same failures could be reproduced with live `logcat`/screenshot visibility — production builds can't be introspected this way.

**1. Root cause of the onboarding hang — Android's own low-memory killer (LMKD), not a logic bug.** Live `logcat` during a reproduced hang at "Tuning quick-recall for your device" showed the app's process being reaped mid-calibration on a Pixel 9 with ordinary background apps open (Facebook, Messenger, Instagram, LinkedIn — confirmed, at the user's explicit correction, to be a normal phone's baseline load, not an edge case: *"Its natural for people to have many apps active in the background at the same time."*). Independently re-verified the calibration code itself was never at fault — closing the other apps and rerunning let the identical code complete in ~2s ("6 threads, 19.8/19.5 tok/s"). This is a genuine OS-level constraint an app cannot override — deciding which process to kill for memory is the OS's own call — so the fix is a three-layer defense that narrows the consequence rather than a false claim of prevention, per the user's explicit bar: *"as a product developer, I can't let an app out on playstore that has a potential to get stuck — not even 1 in a billion."*
   - **Layer 1 — pre-flight check** (`modules/device-cpu/`'s new `getMemoryInfo()`, wrapping `ActivityManager.MemoryInfo`; `services/ai/memoryGuard.ts`'s `checkMemoryBeforeOnboarding()`): runs immediately before the risky calibration step. If Android's own `lowMemory` verdict is already true, onboarding skips the heavier optimistic thread-calibration trial entirely and goes straight to the safe conservative default (see `services/ai/modelDownloadManager.ts`'s `runOnboardingThreadCalibration(skipOptimistic)`), and shows an honest banner (`LOW_MEMORY_WARNING_MESSAGE`) asking the user to close some background apps — the same pattern as an OS "not enough storage" dialog, applied to RAM instead of disk. `null`/unknown readings are treated as safe, never as blocking.
   - **Layer 2 — live monitoring for the whole onboarding sequence** (new `onMemoryPressure` native event via `ComponentCallbacks2.onTrimMemory`/`onLowMemory`; `memoryGuard.ts`'s `watchForMemoryPressure()`): Android reports `TRIM_MEMORY_RUNNING_LOW`/`_CRITICAL` to a still-alive foregrounded app *before* it starts killing background processes for room — the real early-warning window a one-shot check at the start can't see. `components/OnboardingSetupScreen.tsx` subscribes for the duration of the completion sequence and surfaces the same honest banner the moment a signal arrives.
   - **Layer 3 — don't gamble twice, and never leave the user with zero recourse.** `services/settings/preferences.ts` gained `onboardingCalibrationAttemptInFlight` (set immediately before the optimistic trial starts, cleared right after — found still `true` on a fresh launch means the last attempt never got to finish, i.e. the process died mid-trial) and `onboardingStartedAt` (set once, ever, for this install, surviving process kills). A device whose last attempt didn't survive skips straight to the conservative path next time instead of retrying the same risky stretch. Separately, a wall-clock escape hatch (`ESCAPE_HATCH_TIMEOUT_MS`, 3 minutes, measured from the persisted `onboardingStartedAt` so a kill-and-relaunch cycle doesn't reset the clock) surfaces a visible "Continue with Safe Settings" button, so even if a kill happens despite both other layers, the user is never staring at a screen with nothing to do.
   - **Deliberately kept**: optimistic-first calibration stays the *default* path (not switched to always-conservative) — explained to the user as a real trade-off before implementing: always-conservative would be permanently slower for every device's real day-to-day query performance to buy a small reduction in load/reload cycles during the one-time onboarding window, whereas the three layers above bound the actual failure mode directly without paying that ongoing cost. ("Safer" in this design means fewer total model load/reload cycles during the vulnerable stretch, not a reduction in memory footprint — thread count changes CPU parallelism, not RAM usage; corrected mid-explanation after the user's own pointed follow-up questions caught the imprecision.)

## Build 38 — Real-Prefix Boot Warmup, Prefix Harmonization, Retrieval Relevance Floor, Single-Prompt Biometric Unlock

**Origin**: direct continuation of Build 36/37's retrieval-latency work. The user asked pointed technical questions about `llama.rn`'s actual KV-cache behavior (does the context reset per query? would `n_keep` help?) that led to discovering llama.rn already implements automatic longest-common-prefix KV-cache reuse (`find_common_prefix_length` in `rn-completion.cpp`) — confirmed on-device: a second query in the same session already dropped from ~40s to ~6s TTFT with zero code changes. The remaining gaps were: (1) the FIRST query of a session still paid full price (nothing cached yet), (2) a query right after a to-do extraction also paid full price (extraction's totally different prompt evicted the cache), and (3) a genuine retrieval-accuracy bug surfaced independently during testing.

**Fix 1 — real-prefix boot warmup** (`services/ai/localLlama.ts`): the existing silent `prewarmLocalLlama()` warm-up (already running at boot per Build 37) used a throwaway one-word prompt ("Hi"), sharing zero tokens with the real RAG system prompt — so it warmed nothing useful. New `buildCacheWarmupPrompt()` runs the ENTIRE real system prompt + date baseline + few-shot exchange (via `buildPrompt("", "")`) through prefill once, silently, at boot, so the cache is already warm by the time a user's first real question arrives. `WARMUP_PROMPT` (the trivial one) is kept, unchanged, for `attemptTierUpgrade`/`attemptThreadEscalation`'s throughput-measurement trials, which want the cheapest possible prompt.

**Fix 1b — a regression this same fix introduced, found and fixed same day**: making the warm-up this much heavier (~30-40s of real prefill, same cost a cold query used to pay) meant it could now genuinely compete with an active Whisper transcription for CPU if a user recorded within that window — confirmed on-device: a transcription that normally takes ~4.3s took 24.4s while the heavier warm-up ran alongside it. Fixed with `waitForTranscriptionIdleBeforeWarmup()`, mirroring `transformationEngine.ts`'s existing extraction-vs-transcription gate — the warm-up now waits (bounded retries, then proceeds regardless) for any in-flight transcription before starting, since a transcription is always user-facing and the warm-up never is.

**Fix 2 — prefix harmonization** (`services/ai/localLlama.ts`, `services/ai/transformationEngine.ts`): the RAG system prompt and the to-do-extraction system prompt used to open with completely different text, so `find_common_prefix_length` found zero shared tokens between them — meaning any extraction running between two queries fully evicted the cached system prompt, forcing the next query back to a full ~40s cold prefill. New exported `SHARED_XAYRA_PREAMBLE` (identity + the "notes are voice-transcribed, may contain mishearings" note — genuinely useful to both tasks, not artificially padded to hit a token target) is now the literal, word-for-word opening of both prompts. A query landing right after an extraction now gets that much of its system prompt back from cache instead of re-evaluating everything.

**Fix 3 — retrieval relevance floor** (`services/notes/noteManager.ts`): found via a real on-device accuracy failure, not proactively — asking "when do I have to call Papa?" against a 3-note vault returned an answer that blended in a completely unrelated note about testing a Pixel build. Root cause: `hybridSearchNotes`'s reciprocal-rank-fusion scoring is purely rank-based with no minimum relevance score at all — with a small vault (this app's common case), the vector search always returns SOMETHING for every requested slot regardless of how weak the actual match is, and the FTS5 keyword query was OR-ing every word in the spoken question together UNFILTERED, so common function words ("you", "did", "in", "my") matched almost any note. Fixed with (a) `MAX_NOTE_VECTOR_DISTANCE`, a minimum cosine-similarity floor on the vector query, and (b) `FTS_STOPWORDS`, a filter dropping function words from the FTS5 query before it's built. The floor's exact value (0.4) is not a guess — it was calibrated against REAL on-device distance data added specifically for this (a diagnostic `[Retrieval]` log): a genuinely relevant note measured 0.281, three unrelated notes clustered tightly between 0.501-0.531, and 0.4 sits cleanly in that real gap. An initial guess of 0.9 was confirmed on-device to be far too permissive to exclude anything.

**Known remaining gap, not fully solved**: a subsequent on-device test ("summarise all the notes about Varun") still blended in an unrelated note — traced to the confounding note sharing an incidental word ("summarize") with the query itself, which vector similarity picks up on even though it has nothing to do with the actual topic. This is a genuine limitation of embedding-based retrieval for entity-specific questions, not something one global distance threshold can fully close — the user made the explicit, correct call to hold further relevance tuning until testing on the Pixel 9 (the actual target hardware) rather than continuing to calibrate against a 4-note vault on a 1B model.

**Separately found and fixed — the database encryption key required TWO biometric prompts per app launch** (`services/crypto/keyManager.ts`): `readOrCreateKey` called an explicit `LocalAuthentication.authenticateAsync()` prompt AND relied on `SecureStore`'s own `requireAuthentication: true` option, which already gates the read/write behind its own native biometric prompt — fully redundant, confirmed as real testing friction on both the Redmi and Pixel 9. Removed the explicit prompt; the SecureStore-level gate alone provides the identical security guarantee. Also fixed the prompt text, which still said "Unlock Silent Confidant" (pre-rebrand name).

**Closed loop, worth recording**: the user proposed fine-tuning the model on ~100 curated examples so a much shorter prompt (e.g. "You are Xayra. Answer using [NOTES]") could replace the ~1,100-token system prompt entirely, eliminating the warm-up's own cost at the root. Technically sound in principle (behavior distillation is real) — declined for now on practical grounds: ~100 examples is unlikely to reliably generalize across the dozen-plus independent behavioral rules this system prompt encodes (each traceable to a specific documented on-device failure), the iteration loop would go from "edit a string, redeploy in minutes" to "curate data, retrain, re-validate against every prior failure mode, ship a new multi-hundred-MB model," and the win it targets has already shrunk substantially now that Fixes 1-2 above mean the user-facing cost is usually already hidden behind cache reuse. Revisit once the rule set has stabilized and real multi-device usage data justifies the investment.

## Build 36 — Completion-Queue Preemption, Transcription/Extraction CPU-Contention Gate

**Origin**: on-device tester feedback (Redmi Note 8 Pro, after Build 35 shipped) describing exactly the residual contention Build 35's own doc comments already predicted was still possible: "my query took long, perhaps because it was busy creating a to-do" and "the 2nd note's transcription took a while, perhaps because the 1st was busy making a to-do." **Fix 2 — Whisper/Llama CPU-contention gate** (`services/ai/localWhisper.ts`, `services/ai/transformationEngine.ts`): transcription (Whisper) and to-do extraction (Llama) are two entirely separate native engines that never shared any coordination — unlike two Llama completions, which already serialize through the queue above. `localWhisper.ts` now tracks an `activeTranscriptionCount`; `transformationEngine.ts` gates extraction behind a new `waitForTranscriptionIdleIfNeeded()`, mirroring the existing thermal-status gate's exact shape (short retry/backoff, then proceeds regardless rather than blocking a note's extraction forever). Extraction yields to transcription, never the reverse — transcription is always directly user-facing (a "Transcribing..." spinner), extraction never is.

**Also explained to the user**: why the very first note of a session still "feels slow" to transcribe even after these fixes — `localWhisper.ts`'s `getWhisperContext()` lazily loads the GGML model file from disk into native memory on the FIRST call only (logged separately as "Whisper cold-start"), a one-time cost every subsequent transcription skips by reusing the already-loaded context. Not a bug; the same lazy-singleton pattern this codebase already uses for the Llama context.

## Build 35 — Adaptive Thread-Count Calibration (Retrieval Latency Fix), Completion-Queue Race Fix

Commits `b4fe164`, `514a36a`, `e64042c`.

**Origin**: a Pixel 9 tester (12GB RAM, otherwise idle — "1 app used memory in last 3 hours") reported retrieval taking ~2 minutes with only 48 notes, threatening to stop using the app over it. User's own framing reshaped the fix's design mid-session, worth recording verbatim: *"my real users are perhaps going to be the likes of Pixel 9 and after"* — the 2019-era budget test devices in this codebase's own history (Galaxy A50, Redmi Note 8 Pro) are edge-case testing rigs, not the target user base, and the fix should optimize for the common case being a capable device, not the reverse.

**Root cause**: `computeInferenceThreadCount()` (`services/ai/localLlama.ts`) sized Llama's thread pool as `floor(cores / 4)` — a formula reverse-engineered from exactly one device (an 8-core 2019 Galaxy A50 that froze the whole app at HALF that many threads during sustained extraction, see [[todos-freeze-investigation]]). A Pixel 9 is also commonly 8-9 cores, so it received the IDENTICAL "2 threads" — the same category of mistake as the already-fixed RAM-only 1B/3B tier heuristic ([[ram-tier-bad-proxy-for-cpu]]): core count, like RAM, can't tell a capable device from an incapable one. Confirmed directly: the Redmi Note 8 Pro and this Galaxy A50 have the *same* core count but wildly different real capability.

**Design evolution, worth keeping for future reference — this went through two real iterations, not one**:
1. First attempt: conservative-then-escalate (`attemptThreadEscalation`, `maybeAttemptThreadEscalation` in `modelDownloadManager.ts`) — a device earns more threads only after real usage history shows it's struggling. Correctly safe, but can't help a device's *very first* query, since it needs several completions of history before attempting anything.
2. User's explicit pushback (see the quote above) reframed this as solving the wrong common case. Replaced with optimistic-first calibration (`attemptOptimisticThreadCalibration`, `runOnboardingThreadCalibration`): tries an aggressive thread count (reserve only 2 cores for the OS) ONCE, during onboarding's "Tuning quick-recall for your device" step — before the user has asked a single real question, inside a screen they're already waiting through for model downloads. Bounded by a 12s timeout and actually cancellable (`llama.rn`'s `stopCompletion()`), so a device that can't handle it falls back cleanly to the old conservative default with zero risk to onboarding completing. The conservative-then-escalate mechanism from attempt 1 wasn't discarded — it's kept as a SECOND-CHANCE safety net for a device that falls back during onboarding but is actually capable (e.g., a background download competing for CPU at that exact moment).

**A real on-device hang, found and fixed via live logcat debugging, not guessed**: the optimistic calibration hung the app completely during onboarding on first on-device test — no error, no crash. Root cause: `attemptOptimisticThreadCalibration` called `releaseLocalLlama()` directly to tear down the shared context, while `prewarmLocalLlama()`'s own 1-token warm-up completion could still be in-flight on that exact context — releasing a context mid-completion just hangs forever. This is exactly the failure class `runQueuedLlamaCompletion`'s own priority-queue doc comment already warned about ("a native llama.cpp context allows exactly one in-flight operation at a time"), just triggered by a release/reload sequence instead of two competing completions. Fixed with a new `runExclusiveLlamaTask()` sharing the same queue via a `QueuedJob` discriminated union (`"completion" | "task"`) — a task job gets the same mutual-exclusion guarantee a regular completion does, so nothing else can possibly be mid-completion on a context before this tears it down. All three thread-tuning trial functions (tier upgrade, thread escalation, optimistic calibration) now route through it instead of calling `releaseLocalLlama()` directly. Confirmed fixed via before/after logcat: prewarm's completion went from hanging indefinitely to resolving in well under a second.

**Separately found and fixed while debugging this**: `app/_layout.tsx`'s `useSetupGate` had no `.catch()` on `isSetupComplete()` at all — a genuine failure there would leave the setup gate stuck at `null` forever (rendering nothing), with no error surfaced anywhere to explain why. A `.catch()` now logs it. (The actual hang encountered mid-investigation — first-ever encryption-key creation, biometric-gated, unable to complete because the test device's screen was locked — is a separate, pre-existing, already-documented constraint of testing on that specific device, not a bug in this codebase; noted here only because it consumed real debugging time before being correctly ruled out.)

**Confirmed on-device (Redmi Note 8 Pro, screen unlocked per the note above)**: full onboarding-to-home-screen flow completed cleanly, no crashes. Calibration log: `"Onboarding calibration accepted — 6 threads, measured 11.4 tok/s"` — up from this exact device's own historical ~3.1 tok/s at 2 threads ([[ram-tier-bad-proxy-for-cpu]]). This is this project's own worst-case reference device; a genuine flagship (individually faster cores, not just more of them) should see at least as large a relative gain, plausibly larger.

`npx tsc --noEmit` / `npx expo export --platform android` clean after every commit. No native module touched — pure TypeScript/JS throughout, verified via Metro reload + fresh install (uninstall/reinstall to re-trigger onboarding) on the Redmi, not a native rebuild.

   - **`[BLANK_AUDIO]` leaking into saved transcripts** (`ad83749`): whisper.cpp emits its own literal marker as a separate segment for a silent tail/lead within an otherwise-real recording; `noteManager.ts`'s `isSilentTranscript` only ever checked "is the WHOLE transcript nothing," so a real note could be saved with the marker glued onto the end. Fixed at the source in `localWhisper.ts` with a marker-stripping pass.
   - **Fixed VAD loudness floor couldn't hear speech from 2-3m away** (`ad83749`): `activeMode.ts`'s energy-threshold VAD used one hardcoded RMS floor (`0.02`), tuned for arm's-length use — speech from further away never crossed it, so the utterance was discarded before Whisper ever ran. Replaced with per-cycle adaptive calibration: the first 300ms of each listen cycle samples the room's actual ambient noise floor, then sets that cycle's threshold to `noiseFloor × 2.5` clamped to `[0.006, 0.02]` — the upper bound is the OLD fixed value, so a loud room is never worse off, only a quiet one gets meaningfully more sensitive.
   - **Hardcoded wake-word spelling list couldn't keep up with an invented brand name** (`03f2a9d`): "Xayra" has no real pronunciation the on-device `base.en` Whisper model ever saw in training, so it doesn't consistently mishear it as any small fixed set of alternates — confirmed an 8-in-10 miss rate even at clear, close range. `containsWakeWord` now does a bounded Levenshtein edit-distance fuzzy match (distance ≤ 2) against "xayra" over every transcript token, catching a much wider space of misspellings ("Sierra," "Xyra," "Zara") than a literal list, while a real word like "Sarah" (distance 3) stays safely outside the gate.
   - **"Hey Xayra" was being ERASED, not misspelled** (`d70fdef`): root-caused via logcat that "Hey Xayra, can you record my notes?" consistently came back as "his error, can you record my notes?" / "Here is the error, can you record my notes?" — the REST of the sentence transcribed perfectly, isolating the failure to specifically the "Hey" + out-of-vocabulary-word combination (confirmed: saying just "Xayra" with no "Hey" correctly came back as "Zaira," already caught by the fuzzy matcher above). Fixed by priming whisper.rn's `transcribe()` call with `prompt: "Xayra"` — whisper.cpp's `initial_prompt` mechanism, which biases the decoder toward recognizing a word without it needing to be in the model's training vocabulary, at zero extra inference cost.
   - **No gain normalization — quiet/distant recordings lost their first syllable(s) entirely** (`a80f813`): confirmed on-device that 1m worked but 3m was "a mixed bag," with several genuine attempts coming back with the wake word completely absent (`""`, `"."`, a bare leading comma) while the rest of the same sentence transcribed fine — consistent with a real speech phenomenon (an utterance's own first syllable is typically its softest, "onset softness") having no headroom left after distance-based attenuation. `writePcmChunksAsWav` (`services/audio/wav.ts`, shared by manual recording and Handsfree alike) now peak-normalizes the finalized recording up toward 90% of full scale before writing it, capped at 8× gain so a near-silent buffer can't be amplified into loud hiss/static.
   - **THE fix that actually closed out the miss rate — native mic session was being torn down and rebuilt before every utterance** (`726e401`): the previous fix helped but didn't fully resolve it; further logcat testing kept showing the wake word specifically missing at the very START of an utterance while the rest of the same sentence was fine — a pattern that fits a hardware cold-start, not loudness. `armListening()` was calling `AudioRecord.init()` + `.start()` completely fresh on every single utterance boundary (right after `finalizeUtterance()`'s own `AudioRecord.stop()`), not just the first one after engaging Handsfree — real Android audio hardware takes a non-zero moment to start delivering samples after a fresh start, and the wake word (always the first syllable(s) into a freshly-reopened stream) had no room to survive that gap. Fixed by opening the native session exactly ONCE in `start()` and keeping it running continuously for the whole Handsfree engagement; between utterances, only a JS-side `capturing` flag toggles (discarding chunks while not capturing is what still keeps the mic from picking up the assistant's own TTS playback as a new utterance, same protection as before, no longer implemented via an actual hardware stop/restart). **User confirmed this resolved the issue in live testing.**

### Total freeze bug — root cause found, fixed

Opening/using the To-Dos screen on the test device would go **completely unresponsive** — no checkbox, edit, +, back, or scroll — with no crash, no exception, and the JS thread reporting idle. Touches kept dispatching at the OS level but never reached React. This looked, and was investigated, like a UI bug for most of the session.

**UI-layer hypotheses investigated and ruled out, in order** (each a real, defensible fix that stayed in the codebase, but none was the actual cause): `@gorhom/bottom-sheet` dynamic-sizing/fixed-snap-point combinations; a `Keyboard.addListener` + `FlatList.scrollToIndex` fix for a keyboard-covers-input issue; RN's core `<Modal>` opening on a **pushed** `expo-router` route (theorized as an Android `react-native-screens` Fragment-focus bug — fixed anyway by converting `/todos` from a pushed route into `components/TodosOverlay.tsx`, a full-screen root-sibling overlay matching the existing `ExpandedTextOverlay` pattern, commit `4cefbcc`); touchable/gesture-handler harmonization (`Pressable` → `TouchableOpacity` from `react-native-gesture-handler` throughout `TodoItemRow.tsx`/`TodosOverlay.tsx`, since this app's `GestureHandlerRootView` root also hosts `@gorhom/bottom-sheet`, commit `ae12374`). **Fix** (commit `ae2f8ac`): added `modules/device-cpu/` — a tiny local Expo native module wrapping Android's `Runtime.getRuntime().availableProcessors()`, following the exact pattern of the pre-existing `modules/app-signature/` — and changed `localLlama.ts` to size `n_threads = Math.max(1, Math.floor(cores / 4))`, a **proportional** reservation (a quarter of cores for inference, three-quarters left for the OS/UI), computing 2 threads on the 8-core test device (down from the hardcoded 4). A real regression was caught and corrected mid-session before being reported as fixed: an earlier attempt reserved a **flat** number of cores (`cores - 2`), which computed *worse* results (6 threads) on this actual 8-core phone than the original bug — worth remembering for any future device-sizing decision, and the direct reason the fix uses a proportion of cores rather than a flat headroom count (the user explicitly pushed back on tuning the code to one test phone: "this phone isn't the barometer"). Sub-finding: `llama.rn`'s `CompletionParams.n_threads` (a per-call override) does **not** work — confirmed against `llama.rn`'s native C++ source that the ggml threadpool is attached once at `initLlama()` time and nothing calls `llama_set_n_threads()` per completion, so a per-call override for extraction alone (tried and reverted) is a silent no-op; one shared, conservative context-level thread count is the only real lever, slowing down both RAG chat and extraction as an accepted tradeoff.

### To-Do date extraction — chrono-node pre-pass replaces per-miss few-shot growth

A reported "to-dos always land on today regardless of what date the note actually said" bug was root-caused via a temporary raw-input debug log (removed once diagnosed — this app deliberately never logs raw note content elsewhere, see `noteManager.ts`) to a real model-accuracy miss, not a chrono-node resolution bug: a bare imperative voice-note transcript ("Book a movie ticket this Friday.") consistently (temperature 0, fully reproducible) got back an empty `date_phrase` from the 1B extraction model, despite an existing few-shot example with the same date phrase in a different sentence shape.

The user correctly identified that "add one more few-shot example per miss" doesn't scale — unbounded prompt growth, worse mobile TTFT, and it only ever covers phrasing shapes someone happened to hit. **Architectural fix** (commit `334a667`): `detectDatePhrases()` runs `chrono-node`'s `parse()` (not just the existing `parseDate()`) directly on the raw note text **before** the LLM call, independent of the model entirely, and the result is injected into the system prompt as an "answer key" the model is told to copy from exactly. `normalizeExtracted()` then reconciles the model's own `date_phrase` against that same list rather than trusting it outright: a phrase that's neither in the detected list nor a literal substring of the note anywhere is dropped as a hallucination (a new safety net); an empty `date_phrase` on a single-task, non-recurring note where chrono found exactly one candidate is auto-filled with that candidate — the deterministic fix for the exact reproduced miss. Considered and rejected: a dynamically generated GBNF grammar restricting `date_phrase` to exactly the detected phrases (correct in principle, but fragile to hand-write correctly — nested GBNF/JSON string escaping — versus the reconciliation approach's much simpler, more obviously correct code for the same practical guarantee). Performance: `detectDatePhrases()` is synchronous JS on the JS thread (single-digit ms), zero interaction with the shared llama.cpp context or the `n_threads` tuning above; the prompt grows by a handful of tokens, noise against the existing several-hundred-token preamble.

**A regression this introduced, found and fixed in the same pass** (commit `6e59636`): chrono has no concept of a recurrence *cadence* — "Water the plants every 3 days." classified recurrence "daily" correctly, but chrono detected the fragment "3 days" (from inside "every 3 days") as its own one-off relative date, and the single-candidate auto-fill trusted it, producing a wrong one-off action date ~3 days out instead of respecting the recurring schedule. Fixed by resolving recurrence *before* date-phrase reconciliation and only auto-filling from chrono's detection when `recurrence === "none"` — chrono only ever detects calendar dates, never cadences, so its candidates are only trustworthy for non-recurring tasks. Also added a dedicated few-shot example retaining a purely numeric interval phrase ("every 3 days") in `date_phrase`, since no prior example demonstrated that shape and it's the one thing chrono structurally cannot backstop (a cadence phrase can only ever reach `date_phrase` via the model getting it right).

## Build 28 — Duplicate Voice RAG Query Fix (unversioned)

A real bug reported directly against a running on-device build, then root-caused via a live Metro log rather than assumed from the code: asking a spoken question in Ask mode produced **two** full RAG/Llama answers and two user/assistant chat bubbles for one utterance.

- **Root cause, confirmed via a live device log, not guessed**: `app/index.tsx`'s `finishUtterance` called `routeFreeformInput(...)` — which, for the ASK intent, already runs the complete RAG exchange via `chatSession.submitQuery()` (search, Llama generation, append a user+assistant message pair, everything) — and then, once that had already returned, called `chatSession.ask()` a **second time** on the identical transcript. That second call re-ran the entire pipeline from scratch and appended its own redundant message pair. A live log confirmed it directly: two full `SQLite-vec + FTS5 search retrieval` + `Llama total generation` cycles back to back for one spoken question (140s then ~10s — the second one faster only because llama.rn's context was already warm from the first).
- **Why none of Build 25's Atomic Voice Lock guards caught this**: `isSendingRef`/`isProcessingVoiceQueryRef`/`lastVoiceQueryRef` all guard against two *concurrent* calls racing each other on a stale closure. This bug's two calls are strictly *sequential* — the second one starts only after the first has fully finished and every ref/state guard has already reset — so it was never the race those defenses were built for.
- **Fix**: `routeFreeformInput`'s ASK branch now checks whether the call is voice-sourced (`audioUri` present). If so, it calls `chatSession.ask()` directly (the side-effect-free variant, no auto-speech) and returns the answer text to the caller; `finishUtterance` uses that returned text to speak the answer itself via `speakTextAndWait`, and no longer calls `ask()` a second time on its own. A typed (non-voice) ASK is unaffected — it still goes through `submitQuery` exactly as before, since ComposeBar's submit handler never called `ask()` afterward in the first place.
- `npx tsc --noEmit` — clean. Pure JS/TSX change, no native dependency touched — verified live via Metro's fast-refresh reload on the physical A50 (no `prebuild`/native rebuild needed).

## Category B, Item 8: Shower / Hands-Free Active Mode

- **`services/audio/wav.ts`** (new): `buildWavHeader`, `writePcmChunksAsWav`, and the shared `SAMPLE_RATE`/`CHANNELS`/`BITS_PER_SAMPLE` constants were extracted out of `services/audio/recorder.ts` into their own module, plus a new `computeRms()` helper. Both `recorder.ts`'s manual mic flow and the new `activeMode.ts` auto-segmenting loop needed the exact same WAV-assembly logic; `recorder.ts` was refactored to import it rather than keep a second copy.
- **`services/audio/activeMode.ts`** (new): `ActiveModeManager` — a framework-agnostic class driving the continuous "listen → auto-stop on silence → hand off to caller → re-arm" loop, plus a `useActiveMode(onUtterance)` React hook wrapping it for screen components.
  - **VAD approach and its real limitation, stated plainly**: silence detection is a simple RMS (root-mean-square) energy threshold over each incoming PCM chunk — `computeRms()` in `wav.ts`. This is *loudness-based*, not voice-based: it distinguishes "something loud is happening" from "it's quiet," not "that's a voice" from "that's noise." For an ordinarily quiet room this works fine as hands-free VAD. For the feature's own namesake use case — an actual running shower — continuous water noise sits close to white noise and can be loud enough to never drop below the threshold, meaning silence-based auto-stop may not reliably trigger while water is running. A genuinely shower-robust VAD would need spectral/energy-in-speech-band analysis or a real ML VAD model; neither is implemented. Flagging this now rather than letting "Shower Mode" imply it was solved.
  - Utterance boundary: `SILENCE_RMS_THRESHOLD = 0.02`, `SILENCE_HOLD_MS = 1500` (per the task's 1.5s spec), `MIN_UTTERANCE_MS = 400` (guards a stray tap/cough from finalizing as a real utterance), `MAX_UTTERANCE_MS = 60_000` (safety cap for a miscalibrated/noisy environment that never reads as "silent"). All named constants at the top of the file — tune there if the threshold needs adjusting for a real device/environment (untested against actual shower acoustics).
  - **No echo cancellation exists anywhere in this stack.** The critical consequence: the mic must not be capturing while the app itself is talking, or it will "hear" and transcribe its own TTS output as the next utterance. `ActiveModeManager` handles this by fully stopping the PCM capture session before calling `onUtterance`, and not re-arming until that handler's returned promise resolves — the handler is expected to `await` its TTS all the way to completion (see `speakTextAndWait` below), not fire-and-forget it.
  - **`services/audio/tts.ts`** gained `speakTextAndWait()` — `speakText()` itself resolves as soon as `Speech.speak()` is *called*, correct for the existing manual-chat UI (nothing there needs to block on narration finishing) but wrong for Active Mode, which must block the whole loop until speech actually finishes. Guards against the empty-text case, where the underlying `Speech.speak()` call is skipped entirely and its callbacks would otherwise never fire, which would have left the returned promise hanging forever.
  - **Android foreground keep-alive**: implemented via `expo-keep-awake` (installed as a direct dependency — it existed only as a nested transitive dependency of the `expo` package before this pass, not directly importable). `activateKeepAwakeAsync()`/`deactivateKeepAwake()` are tied to Active Mode's own start/stop. **Scope of what this actually covers, stated plainly**: this keeps the screen and CPU awake only while the app is in the foreground — it prevents the device from auto-locking mid-listen, which is the actual "shower" failure mode (phone screen timing out while your hands are wet/busy). It does **not** implement a true Android foreground service, so backgrounding the app or a manual power-button lock still suspends recording. A real background-capable service is a separate, materially larger native undertaking (persistent notification, foreground service permission/type, `expo-task-manager` or a custom native module) — not implemented here, and not what "keep-alive" was scoped to mean in this pass.
- **`components/ActiveModePill.tsx`** (new): the "soft toggle pill" from the task spec, rendered identically on both Notes and Chat headers (same position on both, following the Category A central-mic-button precedent), showing Listening…/Thinking…/Speaking… based on `ActiveModeManager`'s state.
- **Per-tab behavior**:
  - **Notes tab** (`app/index.tsx`): utterance → `asrRouter.transcribe()` → `createVoiceNote()` → `refreshNotes()` → `speakTextAndWait("Saved.")` → re-arm. Silent/empty transcripts are skipped with no note created and no spoken feedback (avoids narrating "Saved" for a false-positive VAD trigger with nothing actually said).
  - **Chat tab** (`app/chat.tsx`): `handleSend`'s message-creation and RAG-generation logic was extracted into a shared `runRagExchange()` so both the manual send flow and Active Mode append to the same visible chat transcript and hit the same code path — utterance → transcribe → `runRagExchange()` → `speakTextAndWait(answer)` → re-arm.
  - Both screens disable their manual mic button (and Chat additionally disables the text input/Send button) while Active Mode is engaged, since `@fugood/react-native-audio-pcm-stream` supports only one capture session at a time and `ActiveModeManager` owns its own session independent of `useVoiceRecorder`.
  - Errors during an Active Mode utterance are logged, never surfaced via `Alert` — a hands-free loop shouldn't interrupt itself with a dialog the user may not be positioned to dismiss (wet hands, phone across the room). The loop always re-arms in a `finally`, so one failed utterance doesn't end the session.
- `npx tsc --noEmit` — clean, zero errors.

```
  at com.imxiqi.rnliveaudiostream.RNLiveAudioStreamModule$1.run(RNLiveAudioStreamModule.java:103)
```
Root cause, found by reading the native source directly: `@fugood/react-native-audio-pcm-stream`'s background recording thread re-reads a shared **mutable instance field** (`recorder`) fresh on every loop iteration instead of capturing a stable local reference at thread-start. A concurrent `stop()`/re-`init()` (from a second recording session starting before the first thread has fully exited — a real scenario any time a session is stopped and quickly re-armed, exactly what Active Mode's loop does) can null or reassign that field mid-loop, so the next `.read()`/`.release()` call NPEs. This is a genuine upstream thread-safety bug, not something fixable from the JS side — no amount of delay/sequencing in `activeMode.ts` prevents a race that lives entirely inside the native module's own `Thread.run()`.

**Fixed via `patch-package`**, following this repo's established convention for broken native dependencies (see CLAUDE.md): `RNLiveAudioStreamModule.java`'s recording thread now captures `recorder` into a `final` local (`activeRecorder`) once at thread-start and operates on that stable reference for its entire lifetime, only clearing the shared field in its `finally` block if it still points at the same object (so a newer session's recorder is never clobbered by an older thread's cleanup). Patch lives at `patches/@fugood+react-native-audio-pcm-stream+1.1.4.patch` (54 lines — clean, targeted diff, no build-cache noise per the CLAUDE.md warning about that). Verified the fix with an incremental rebuild (`npx expo run:android`, no `prebuild --clean` needed since this was a Java-only change — `BUILD SUCCESSFUL in 43s`, confirmed `fugood_react-native-audio-pcm-stream:compileDebugJavaWithJavac` actually recompiled rather than reusing cache) and then stress-tested with 5 rapid on/off toggles in a row on-device — same PID survived throughout, zero crash traces in logcat afterward. The original bug was a timing-dependent race (not deterministic), so the repeated-toggle stress test matters more here than a single clean pass would.

## Post-Phase-4 Runtime Fixes — found and fixed via actual on-device testing

Phase 4's earlier "100% COMPLETE" declaration was based on a successful native **build** (compiles and links) — that's a weaker claim than "actually works." Two real runtime bugs surfaced once the app was actually exercised on-device, and both are now fixed **and confirmed live**, network off, on the `Pixel_6` emulator:

**1. ONNX crash: `[TypeError: Cannot read property 'install' of null]`**
- Root cause: `onnxruntime-react-native` ships an `app.plugin.js` (Gradle/Podfile dependency wiring only). Expo's autolinking treats any package with an `app.plugin.js` as "self-handled" and skips it from the classic community-autolinking pass that generates `PackageList.java` (the file that actually registers native modules on the bridge). So `OnnxruntimeModule` never got registered despite its C++ code compiling fine — `NativeModules.Onnxruntime` was `null` at runtime, crashing on `Module.install()`. The two Metro "Route is missing the required default export" warnings on `chat.tsx`/`index.tsx` were a downstream symptom, not a real bug — both files genuinely have `export default`; a module-scope import throwing during evaluation poisons the whole route's module graph before Metro can inspect its exports.
- Fix: project-root `react-native.config.js` explicitly declaring `onnxruntime-react-native`'s Android dependency config, which overrides the "has app.plugin.js, skip it" heuristic. First attempt had a bug — `sourceDir` was written relative to the *app root* (the classic RN CLI convention) but this Expo autolinking implementation joins `sourceDir` onto the *package's own directory*, so it resolved to a doubled `node_modules/node_modules/...` path and silently failed. Caught by reading `expo-modules-autolinking`'s resolver source directly rather than trusting the first rebuild's output. Verified by confirming `new ai.onnxruntime.reactnative.OnnxruntimePackage()` actually appears in the generated `PackageList.java`, and by the ONNX-dependent embeddings migration succeeding at runtime (`[db] Background re-embedding migration complete: 2/2 notes.`).

**2. Recording crash: `{ message: 'Invalid WAV file' }` from whisper.rn**
- Root cause: `services/audio/recorder.ts` used `expo-audio`'s `RecordingPresets.HIGH_QUALITY`, which records `.m4a` (AAC) on Android — a leftover from when this app used OpenAI's cloud Whisper API (which accepts AAC fine). `whisper.rn`'s README is explicit: *"Compressed formats such as MP3, AAC, and FLAC are not decoded."* Every local voice-note transcription had been silently broken since Stage 4A; it only surfaced once tested with the network genuinely off. Android's `MediaRecorder` (what `expo-audio`'s recorder uses) has no WAV/raw-PCM output option at all — an OS API limitation, not a config gap, so no preset tweak could fix this.
- Fix: rewrote `services/audio/recorder.ts` to capture raw 16-bit mono PCM directly at 16kHz via **`@fugood/react-native-audio-pcm-stream`** (verified on npm: MIT, same publisher org as `whisper.rn`/`llama.rn`, and literally the library `whisper.rn`'s own bundled realtime-transcription module is built around) and hand-assembles a WAV file from the streamed chunks (44-byte header + concatenated PCM, written in one shot — voice notes are short enough that in-memory buffering is simpler and safer than incremental disk writes). A short `STOP_DRAIN_MS` grace period after `stop()` avoids losing the tail of the recording, since the native module's `stop()` just flips a flag and its read loop exits asynchronously. `types/fugood-audio-pcm-stream.d.ts` (new) works around the package's own `.d.ts` declaring itself under its pre-rename npm name (`react-native-live-audio-stream`) rather than its actual scoped package name — the same class of fix as `whisper.rn`'s `tsconfig.json` `paths` override from Stage 4A, just via an ambient module declaration this time since the mismatch is the declared name itself, not resolution.
