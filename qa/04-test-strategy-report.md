## 2. Tool recommendation per layer

All of the following are **proposals only** — no package was installed, no config file was written, per the audit-only constraint.

### 2a. Pure logic in `services/` — Jest via `jest-expo`

**Recommendation**: `jest-expo` as the Jest preset. It ships Expo/React-Native-aware transform config (handles `expo-*` package internals, asset mocks, `import.meta` in some RN/Expo interop shims) out of the box, which a bare `jest` + `babel-jest` setup would otherwise require hand-rolling module-by-module.

Proposed setup:
- `devDependencies`: `jest`, `jest-expo`, `@types/jest`.
- `package.json`: `"scripts": { "test": "jest" }`, `"jest": { "preset": "jest-expo" }` (or a standalone `jest.config.js` with `module.exports = { preset: "jest-expo" }` — either is fine; a standalone file is easier to layer `testPathIgnorePatterns`/`transformIgnorePatterns` onto later).
- Target first: pure-function modules with no native import at module-eval time — `services/todos/todoManager.ts`'s `computeNextActionDate()` (`services/todos/todoManager.ts:401`), `services/notes/noteManager.ts`'s `toFtsQuery()` (`services/notes/noteManager.ts:661`), `utils/greeting.ts`'s `getTimeBasedGreeting()` (`utils/greeting.ts:8`), `services/ai/pipelineStage.ts`'s pub/sub (`services/ai/pipelineStage.ts:33-48`, no native deps at all — the single easiest module in the codebase to reach 100% coverage on). These need zero mocking because they import nothing from `op-sqlite`/`llama.rn`/`whisper.rn`.
- Caveat found during this audit: several "pure logic" modules are not actually import-clean — e.g. `noteManager.ts` imports `db/client.ts` at module scope, which opens an `op-sqlite` connection as a side effect of import. Testing `toFtsQuery()` in isolation therefore either requires (a) extracting it to a small standalone module with no DB import (a real, minimal refactor — flagged, not performed), or (b) mocking `db/client.ts` via `jest.mock()` even though the function under test doesn't touch the DB. Recommend (a) opportunistically whenever one of these functions is next touched for an unrelated reason, since it also makes the function easier to reason about in isolation.

### 2b. Anything touching `llama.rn`/`whisper.rn`/`op-sqlite`/`expo-local-authentication` — Jest + mocked native modules

**Recommendation**: same Jest/`jest-expo` runner, with `jest.mock('llama.rn', ...)` / `jest.mock('whisper.rn', ...)` / `jest.mock('@op-engineering/op-sqlite', ...)` / `jest.mock('expo-local-authentication', ...)` per-suite, backed by small hand-written fakes (not auto-mocks — these libraries' real behavior, e.g. op-sqlite's `db.transaction()` semantics, is exactly what several of the backlog items below need to *simulate*, not stub away).

Proposed setup, additive to 2a:
- A `__mocks__/` directory (Jest's own convention) or inline per-test `jest.mock()` factories for each of the four native modules, since Jest cannot load their real native bindings in a Node test environment at all (they require a compiled Android/iOS host).
- Concretely: a fake `op-sqlite` `open()` that returns an in-memory JS object implementing just `execute()`/`transaction()`/`executeSync()` against a plain array/Map, enough to test `services/notes/noteManager.ts`'s and `services/todos/todoManager.ts`'s write-path *sequencing* (does the code call `insertEmbedding` then `updateNoteStatus` as two calls or wrap them in one `transaction()`?) without needing a real SQLite engine. This is the right tool for locking in "is this write path transactional" as a structural fact, cheaply and deterministically — see backlog items 4-6.
- A fake `llama.rn` whose `completion()` resolves/rejects on manual control (a `deferred` promise the test holds), enough to test `services/ai/localLlama.ts`'s queue/preemption ordering (`processCompletionQueue`, `services/ai/localLlama.ts:780-876`) without ever loading a real 1B/3B model.
- This layer is deliberately narrower than end-to-end: it proves *this app's own orchestration code* calls the native APIs in the right order/shape, not that the native library itself behaves as documented (that gap is what section 4/5 below calls out as unavoidably needing real hardware).

### 2c. Component-level behavior — React Native Testing Library (RNTL)

**Recommendation**: `@testing-library/react-native` on top of the same `jest-expo` runner. It renders React Native component trees in Node (via `react-test-renderer` under the hood) and queries by role/text/testID rather than snapshotting implementation details — the right fit for this app's component-level risk (the `<Modal>` + `router.push` dead-touch-input bug class Agent 1 re-audited, the audio-source-ownership gaps Agent 2 found at the component call-site level rather than deep in `services/`).

Proposed setup, additive to 2a/2b:
- `devDependencies`: `@testing-library/react-native`, plus its peer expectation matchers are bundled since v12 (no separate `jest-native` package needed at current versions — verify exact version compatibility with React 19.2/RN 0.86 at install time, since this app is on unusually current versions of both).
- Target first: `components/NoteCard.tsx`, `components/ChatSheetContent.tsx`, `components/NoteDetailModal.tsx` — specifically testing that tapping their "play"/"Listen" affordance checks `recorder.isRecording`/`activeMode.isActive` before calling `playUri()`/`speakText()` (see backlog item 3, directly locking in Agent 2's Finding at `qa/02-audio-engine-report.md` row 3). This requires mocking `services/audio/player.ts` and `services/audio/tts.ts` as simple jest mocks returning resolved promises — RNTL only needs to assert the mock *was or wasn't called*, not that real audio played.
- Not a fit for full-screen flows spanning `app/index.tsx`'s ~1000+ lines of interlocking refs/effects (recorder, Handsfree, cancel gesture, quick-menu popover) — that screen's real risk is cross-module timing (audio focus, native mic state) RNTL's simulated renderer cannot exercise. Reserve RNTL for individual `components/*.tsx` files with a narrow, mockable dependency surface; route `app/index.tsx`-level flows to the E2E layer (2d) instead.

### 2d. True on-device E2E — Detox vs. Maestro: **recommend Maestro**, not Detox

The plan explicitly asks for one explicit choice, not a list. Reasoning specific to this codebase:

- **Detox** requires a from-scratch native test-runner integration: a `.detoxrc.js`, a dedicated `android/app/build.gradle` test variant, and — critically for this app — Detox's synchronization mechanism (waiting for the JS thread/timers/network to go idle before proceeding) is built around assumptions that this app's own architecture actively violates: a `llama.rn` completion or `whisper.rn` transcription runs on a native JNI thread for tens of seconds to minutes (the codebase's own doc comments cite a **140+ second** extraction and a **24.4 second** transcription under contention — `services/ai/localLlama.ts:1076-1089`'s doc comment, cited in `qa/02-audio-engine-report.md` row 4), which is exactly the kind of long-lived non-JS async work Detox's idle-detection is known to handle poorly without extensive custom `idlingResource`-equivalent work on Android. That custom work would itself be nontrivial native Kotlin, which this project's own `modules/` pattern shows is not a casual undertaking here.
- **Maestro** drives the app via the Android accessibility tree / UI Automator from *outside* the process, with explicit `waitForAnimationToEnd`/timeout-based steps rather than JS-thread-idle detection — it does not care whether a `llama.rn` completion takes 2 seconds or 2 minutes, because it never tries to synchronize with the JS event loop at all. Given this app's core loop is defined by long-running native inference calls (its entire "Zero-cloud-API... local-first AI" premise per `CLAUDE.md`), this is a structural fit, not a minor convenience.
- Maestro's setup is also dramatically lighter for this specific team: a single `maestro` CLI binary (no Gradle/Xcode project wiring) and YAML flow files, which lowers the bar for whoever picks up E2E work next given this project has zero existing test-authoring conventions to build on.
- **Concrete setup steps (proposed)**: install the `maestro` CLI (documented via `curl -Ls "https://get.maestro.mobile.dev" | bash` on the Maestro docs — not run here), a `.maestro/` directory of YAML flows in the repo root, each flow targeting one already-built `.apk` (built via the existing `npx expo run:android` — Maestro does not replace that build step, only drives the resulting installed app). First flows to write (see backlog item 10): `record-transcribe-save.yaml` (tap record → speak → tap stop → assert a new note card appears in the list), `ask-and-answer.yaml` (open chat → type a question → assert an answer renders within a generous timeout), `onboarding-happy-path.yaml` (fresh install → tap through setup → assert landing on "Start Capturing Thoughts").
- Both tools require a real or emulated device with the actual native binaries (`llama.rn`, `whisper.rn`, `op-sqlite`) compiled in — see `CLAUDE.md`'s own native-rebuild section — so either choice's flows can only run against a dev-client or release build produced by `npx expo run:android`, never against plain `npx expo export`. This is unavoidable given the "Native modules that require a compiled dev client" list in `CLAUDE.md`.

## 4. What can never be fully automated — and why, explicitly

Per the brief: state plainly, not invent a fictional test, wherever a finding is fundamentally an OS-level or hardware-level event.

- **LMKD/OS-level memory-pressure kills** (Build 40's root-caused onboarding hang; the mechanism Agent 1 flags as still-live risk given `releaseLocalLlama()`/Whisper's native footprint staying resident through backgrounding). Android's low-memory killer is a real-device, real-multi-app-load phenomenon — it cannot be triggered from a Jest process or even reliably from an emulator, because it depends on genuine system-wide memory contention across other real apps (Facebook, Messenger, Instagram, LinkedIn were the actual culprits in the original Pixel 9 repro per `PROJECT_STATE_HANDOFF.md`'s Build 40 section). No CI pipeline can reproduce this. It stays a **manual device-smoke checklist item** (section 5).
- **Native C++ heap OOM kill mid-completion.** As Agent 3's report states explicitly and correctly, a whole-process native OOM kill is not a JS-catchable event by definition — there is no `try/catch`, no test harness, no mock that can simulate "the process no longer exists" from inside that same process. The only thing testable here is the *resumability* of whatever durable on-disk state a fix leaves behind (see backlog item 3's "once a fix lands" positive-test path) — never the kill event itself.
- **MIUI-specific notification throttling** (Redmi Note 8 Pro's documented behavior, per the plan's own diagnosis section). This is a vendor-specific OS customization with no public API surface to query or simulate; it can only be observed by actually receiving a scheduled `expo-notifications` local notification on a real MIUI device and checking whether it fired on time.
- **Wi-Fi-speed-dependent onboarding downloads** (the Redmi's 2.4GHz-network 2.5-hour download vs a ~15-minute expectation, per the plan's diagnosis section). Real network throughput variance is not meaningfully mockable in a way that predicts real-world behavior — a mocked slow `fetch`/`DownloadManager` proves the *app's* handling of a long download (progress UI, cellular-consent gating, resumability across a kill) but not whether a specific device/network combination will actually take that long. The app-logic half (resumability across a kill via `nativeDownloadIds`, already confirmed "known-safe" by Agent 1) is unit-testable; the network-condition half is not.
- **Audio-source-ownership gaps requiring real hardware** (Agent 2's Findings 1-3: recording vs TTS/playback, Handsfree vs TTS/playback). The *code-level* fix (does `startRecording()` call `stopSpeech()`?) is unit/RNTL-testable per backlog items 3-5 above. What is **not** testable outside real hardware: whether the actual Android `AudioRecord`/TTS engine genuinely stops producing/consuming audio in time to prevent audible bleed-through, whether a real Bluetooth/wired headset disconnect mid-recording behaves as the mocked test assumes, and whether real audio focus is actually granted/revoked as expected when another app takes it. These require a physical device with a real microphone and real speaker output — no emulator or CI runner meaningfully approximates them.
- **A phone call arriving mid-Handsfree-listening** (explicitly called out by the plan as untested by the closed 5-bug wake-word chain) — requires a real telephony stack (SIM or emulated cellular radio) interrupting a real active `AudioRecord` session; not reproducible from Jest/RNTL/Maestro without a real or telephony-emulated device.

## 5. Manual device-smoke-test checklist

Named against the real device pool already in use per the plan/memory (**Pixel 9**, **Redmi Note 8 Pro**, **Galaxy A50**), covering exactly the categories section 4 says automation cannot reach.

### 5a. Memory-pressure / LMKD (primary device: Pixel 9 — where Build 40's original repro happened)
- [ ] Open 4-5 real background apps (a browser, a social app, a messaging app, a maps app) to approximate the Build 40 repro's real-world baseline load, then run onboarding end-to-end; confirm the three-layer defense (`services/ai/memoryGuard.ts`) either completes calibration or gracefully shows the conservative-path banner — never a silent hang.
