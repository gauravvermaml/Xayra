# Phase 2 Execution Brief — Audio & Recording Resilience

Built from `qa/05-consolidated-triage.md`'s backlog and `qa/06-phase-execution-roadmap.md`'s roadmap-level scoping, now detailed to the same depth as Phase 1's brief. **No code has been changed under this document.** All line citations below were re-verified against the current source just now, not copied stale from the original agent reports — `services/audio/*`, the three playback-triggering components, and `services/ai/transformationEngine.ts`/`localLlama.ts`'s contention gate were untouched by Phase 1, so their original citations still hold; `app/index.tsx`'s line numbers shifted slightly from Phase 1's own edits and are corrected here.

## One lesson from Phase 1, carried into this brief's test design

Phase 1's SQLite fix passed every unit test against a hand-built fake, then deadlocked on real hardware — because the fake didn't model a real reentrancy behavior in the actual library. Phase 2's riskiest area is exactly this kind of gap: audio hardware timing, real TTS engine behavior, and real `AudioRecord`/focus semantics cannot be faithfully mocked at all. This brief is explicit throughout about which claims a unit/RNTL test can actually prove (the code calls the right function in the right order) versus which claims only a real device can prove (the audio actually goes silent in time) — and treats the second category as a first-class deliverable, not an afterthought, rather than repeating Phase 1's overconfidence in mock fidelity.

## 2. Test infrastructure for Phase 2

Adds React Native Testing Library on top of Phase 1's existing Jest base (`jest.config.js`, `jest-expo` preset) — no changes to the existing config's core, just new dependencies and a new class of test file.

**One-time setup** (proposed, not yet installed):
- `devDependencies`: `@testing-library/react-native` — verify exact version compatibility with this project's React 19.2/RN 0.86 at install time (both are unusually current versions; the library's own peer-dependency range needs checking before pinning).
- No new native mocking layer needed beyond what items 1-3 already require: `services/audio/player.ts` and `services/audio/tts.ts` mocked as simple call-recorders (`jest.fn()`), since RNTL only needs to assert the mock *was or wasn't called* — not that real audio played.

**Tests to write, mapped to the items above:**

1. *(item 1)* `startRecording() calls stopSpeech() and pauses playback before opening the mic` — mock `tts.ts`/`player.ts`, call `recorder.startRecording()`, assert both were invoked before the native record call. Pure Jest, no RNTL needed (this is a service-level test, not a component one).
2. *(item 2)* `ActiveModeManager.start() calls stopSpeech()/pause before beginning noise-floor calibration` — same mock pattern, assert call ORDER specifically (stop-then-calibrate, not calibrate-then-stop) since the timing is the actual bug, not just whether the call happens at all.
3. *(item 3)* `NoteCard/ChatSheetContent/NoteDetailModal's play button no-ops while recording or Handsfree is active` — this is the one that genuinely needs RNTL: render each component with `recorder.isRecording: true` (or `activeMode.isActive: true`) injected via whatever prop/context threading the fix introduces, simulate a tap, assert `playUri`/`speakText` were NOT called. Three near-identical test files (or one parameterized test) since the same bug repeats across three components.
4. *(item 5)* `A native "error" event surfaces a user-visible alert and does not finalize a broken note` — this one is **only partially unit-testable**: the JS-side listener wiring and its resulting alert/toast can be tested with a mocked native module emitting a synthetic `"error"` event; whether the REAL native patch actually emits that event on a REAL permission revocation cannot be — that half moves to the manual checklist below.
5. *(item 6)* `waitForTranscriptionIdleIfNeeded/BeforeWarmup eventually proceeds past a transcription lasting longer than the old 6s cap` — mock `isTranscriptionInProgress()` to stay `true` for e.g. 10s then flip `false`, assert the gate doesn't give up before it actually clears (whatever the new schedule/timeout ends up being) — a direct regression lock against the exact gap the finding names.
6. *(item 7)* `An AppState background->active cycle resyncs Handsfree's isActive/state rather than leaving it stale` — mock `AppState`, fire a background-then-active sequence, assert the resync path runs.
7. *(item 10)* `Navigating away from Home stops an in-progress manual recording, not just Handsfree` — mock `recorder.stop`, simulate the existing blur-cleanup `useFocusEffect` firing, assert `recorder.stop` is now ALSO called (currently only `activeMode.stop` is).
8. *(item 11)* `A transcription in progress causes the active download loop to throttle/pause its polling` (or vice versa, depending on the chosen fix direction) — same mocking pattern as item 5's Whisper/Llama gate test, applied to the download loop instead.

**Explicitly NOT attempted as automated tests, moved to the manual checklist below**: item 4 (does backgrounding mid-recording actually lose audio on a real device — needs real `AudioRecord` behavior under real OS backgrounding restrictions), item 5's native-error-actually-fires half, item 8 (real audio-focus grant/revoke from a real phone call or another app), and every claim in items 1-3 about whether real audio genuinely goes silent *in time* to prevent audible bleed-through (the code-level "was the function called" claim is tested above; the acoustic claim is not).

## 3. Verification criteria for completing Phase 2

- [ ] All new Jest/RNTL tests pass (exact count TBD once item 3's exact prop-threading design is settled).
- [ ] `npx tsc --noEmit` clean.
- [ ] `npx expo export --platform android` clean.
- [ ] **No native rebuild required for items 1-3, 6, 7, 10, 11** — pure JS/TS. **Item 5 DOES require a native rebuild** (`npx expo prebuild --clean --no-install` + `npx expo run:android`) since it touches a `patches/` file and the native Android PCM-stream loop, per `CLAUDE.md`'s own rule.
- [ ] **Named regression check against all 5 previously-closed wake-word bugs**, re-run live one more time after these changes — Findings 2/3 (items 2/3 above) touch the exact adaptive-VAD-calibration and no-echo-cancellation mechanisms those fixes depend on, so this phase is the highest-risk one yet for reintroducing a wake-word regression.
- [ ] **Manual device-smoke checklist**, run on all three pool devices where practical (Pixel 9, Redmi Note 8 Pro, Galaxy A50 — adjusted for whichever are actually available at execution time):
  - Tap "Listen" on a past answer, then tap record before narration finishes — confirm by LISTENING to the resulting note's playback for bleed-through, not just checking a function was called.
  - Engage Handsfree while TTS/playback is audibly active — confirm no early false wake-word trigger in the first utterance cycle.
  - While Handsfree is listening, tap "Listen" on an unrelated past answer — confirm no spurious utterance/to-do gets created from the assistant's own voice.
  - Background the app mid-recording (real home-button press, not just a Home intent) — confirm honest behavior (either the recording completes correctly, or the user is clearly told it didn't — never silent data loss with no explanation), matching whatever scope item 4 actually lands at.
  - Revoke mic permission mid-recording via Android Settings — confirm a visible error, not a silent empty note.
  - Record while a model download is actively in progress — confirm transcription speed is back to something close to baseline (or, if the chosen fix direction pauses the download instead, confirm the download resumes correctly once transcription finishes).
- [ ] Each of the fixes above lands as its own separate, reviewable commit, same discipline as Phase 1.
- [ ] This brief, `qa/05-consolidated-triage.md`, and `qa/06-phase-execution-roadmap.md` updated to mark Phase 2's items closed (or explicitly deferred, for anything the scoping conversation on item 4 or the product decision on item 9 pushes out), with the same honest "shipped and verified" vs. "attempted, found broken, reverted" distinction Phase 1 used throughout.
- [ ] Explicit sign-off from you before Phase 3 execution begins.
