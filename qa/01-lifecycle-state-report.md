## Narrative

### Native heap lifecycle (★ New)

**Does anything release `llama.rn`/`whisper.rn` context on backgrounding today? No — confirmed, not assumed.**

- `services/ai/localLlama.ts:1134` exports `releaseLocalLlama()`. A full-repo grep for `AppState` returns exactly one hit, and it's inside `qa/QA_STABILIZATION_PLAN.md` itself — there is no `AppState` import, listener, or subscription anywhere in `app/`, `components/`, `services/`, or `modules/`. Every real call site of `releaseLocalLlama()` is internal to `localLlama.ts` (`attemptTierUpgrade` line 420, `attemptThreadEscalation` line 488, `attemptOptimisticThreadCalibration` line 571) — all three are onboarding/calibration trials that release-then-immediately-reload the context as part of a measurement, never a "the app went to the background, free this up" policy. `PROJECT_STATE_HANDOFF.md:649` independently corroborates this, describing `releaseLocalLlama()` as "now-exported-but-unwired."
- `services/ai/localWhisper.ts` is worse: whisper.rn's own `WhisperContext` type declares a `release(): Promise<void>` method and a package-level `releaseAllWhisper()` (`node_modules/whisper.rn/lib/typescript/index.d.ts:54,79`), but this app's Whisper wrapper never calls either — `grep -n "release" services/ai/localWhisper.ts` returns nothing. There isn't even an unwired export to point a future fix at; the release path for Whisper's native heap footprint would have to be written from scratch.
- **Is this the actual mechanism behind the documented Build 40 LMKD onboarding kill?** Plausible and consistent, though not provable from static code alone. What's confirmed: by the time `OnboardingSetupScreen`'s completion sequence runs (`components/OnboardingSetupScreen.tsx:197-243`), both the Whisper and Llama models have just finished downloading and are being calibrated/warmed (`runOnboardingThreadCalibration`, `attemptOptimisticThreadCalibration` in `localLlama.ts:555-617`) — meaning the app's own resident footprint is at its peak (multiple hundred MB to multi-GB, per `localLlama.ts:403`'s own note about a 3.6GB RSS for a 3B context) at exactly the moment `memoryGuard.ts`'s `checkMemoryBeforeOnboarding()`/`watchForMemoryPressure()` are watching for LMKD-adjacent pressure signals. Since nothing releases that footprint even after a successful calibration, the app carries its heaviest resident set through the exact window Build 40's own investigation already found LMKD reaping it in. This is a real, independent contributing factor to flag — not proven to be *the* root cause (that investigation, per memory, already root-caused the specific Build 40 kill to real multi-app background pressure via live logcat, not to Xayra's own footprint specifically) but a mechanism the same class of report would recur under, since nothing here has changed since Build 40 shipped.
- Concrete, named recommendation (not implemented — this is audit only): an `AppState` listener belongs in **`app/_layout.tsx`**, alongside the existing `useSetupGate()` hook, since that's the one file mounted for the entire app process's lifetime regardless of which screen is showing (both the onboarding screen and the real `Stack` render underneath the same root component). A `useEffect` there subscribing to `AppState.addEventListener("change", ...)` and calling `releaseLocalLlama()` (and, once written, an equivalent Whisper release) when the state transitions to `"background"` would centralize this — the alternative of adding it separately to every screen that happens to touch Llama/Whisper is exactly the "inconsistent survival boundary" risk the QA plan's diagnosis section calls out. **Cost side, per the plan's own instruction — reported, not fixed**: a naive "release on any backgrounding" policy would need to NOT fire while an onboarding download is still in flight (releasing mid-calibration-trial is already documented in `localLlama.ts:547-554` to hang the app when done outside the exclusive-task queue), and would need to NOT fire while a recording/RAG answer/extraction is actively using the context — seeAgent 3's queue-race sub-section below for why this is a genuine, not just theoretical, concern.

**Which multi-statement write paths are transactional, and what happens if a kill lands between statements where they aren't?**

**FTS5 external-content trigger safety** — confirmed safe, contrary to the plan's open question. `notes_fts`'s sync triggers (`db/schema.ts:168-185`) fire `AFTER INSERT`/`UPDATE`/`DELETE` on `notes`. Since each of `noteManager.ts`'s individual `db.execute()` calls (outside an explicit `db.transaction()`) runs as SQLite's own implicit single-statement transaction, and a SQLite trigger's execution is part of the same implicit transaction as the statement that fired it, there is no window in which a single `INSERT`/`UPDATE`/`DELETE` on `notes` can commit while its corresponding `notes_fts` trigger does not — they are atomic with each other at the SQLite engine level regardless of anything this app's own code does. The real risk in this codebase is never `notes` vs. `notes_fts` disagreeing; it's `notes` vs. `note_embeddings` disagreeing, because those two are written from **two separate top-level statements** in application code (see table above), not one statement plus its trigger.

**Does a killed-mid-write transaction roll back cleanly on next open?** Yes, and this is a property of SQLite itself, not something this app's code configures. `db/client.ts` never issues `PRAGMA journal_mode` or `PRAGMA synchronous` anywhere (confirmed by grep), and `package.json`'s `"op-sqlite"` block only sets `sqliteVec`/`fts5` (`package.json:65-68`) — so the connection runs on SQLite/SQLCipher's compiled-in rollback-journal defaults. SQLite's rollback-journal mode is specifically designed to be crash-safe: on next open, an unfinished journal is detected and rolled back automatically before any other access proceeds. Also confirmed the `db.transaction()` primitive itself is real, not a no-op wrapper: `node_modules/@op-engineering/op-sqlite/src/functions.ts:205-290` shows it literally issuing `executeSync('BEGIN TRANSACTION;')`, running the callback, then `COMMIT;` on success or `ROLLBACK;` on any thrown error — this is genuine SQLite transaction semantics, not just a JS-level try/catch pretending to be one. This entire area is marked "known-safe" below, with one caveat noted in the findings table: nobody has ever *deliberately reviewed and pinned* this journal-mode default, so a future performance-motivated change (e.g. someone adding `PRAGMA journal_mode=WAL` without re-examining op-sqlite's own JS-side transaction queue/lock semantics) is a change Agent 3's concurrency model would need to revisit, not a currently-live risk.

## Known-safe, checked and fine

- **`db.transaction()` is a genuine atomic transaction**, not a cosmetic wrapper — verified against `node_modules/@op-engineering/op-sqlite/src/functions.ts:205-290` (real `BEGIN`/`COMMIT`/`ROLLBACK`). `deleteNote()`, `completeToDo()`, `purgeAllNotes()`, `mergeMissingNotes()`, and `mergeMissingToDos()` all correctly use it and were read end-to-end to confirm every statement inside each transaction body actually needs to be atomic with the others (no over- or under-scoped transaction found).
- **FTS5 (`notes_fts`) can never disagree with `notes`** from a killed process — trigger execution is part of the same implicit SQLite transaction as the statement that fires it (see narrative above). The plan's hypothesized "kill mid-write leaves `notes_fts` referencing a rowid `notes` no longer agrees with" risk does not apply to single-statement writes; it would only matter if a future change moved multiple `notes` writes for one logical operation across statement boundaries in a way that also touched FTS mid-sequence, which nothing in this codebase currently does.
- **`insertEmbedding()` is genuinely idempotent** (`noteManager.ts:210-223`) — it always re-resolves the note's current `rowid` and uses `INSERT OR REPLACE`, so calling `tryEmbedNote()` twice for the same note (the exact scenario the plan raises — `retryPendingEmbeddings()` racing `mergeMissingNotes()`'s own fire-and-forget embedding pass) cannot produce a duplicate or conflicting `note_embeddings` row.
- **The rollback-journal crash-safety guarantee is real** and not undermined by anything in this app's connection setup — no `PRAGMA synchronous=OFF` or similar durability-weakening override exists anywhere.
- **No new `<Modal>` + `router.push`/`router.replace` instance found.** Every current native `<Modal>` usage (`components/NoteDetailModal.tsx`, the only one in the codebase — `grep -rn "<Modal" .` confirms) was traced through all three of its mount sites (`app/index.tsx:1066-1071`, `app/archive.tsx:154-162`, `components/TodosOverlay.tsx:259-263`) and none of their `onClose`/`onDeleted` callbacks call `router.push`/`router.replace` — they only clear local state (and, in Archive's case, refresh the notes list). `components/ChatSheetContent.tsx`, `components/ComposeBar.tsx`, and `components/AddTodoBottomSheet.tsx` contain no `<Modal>` at all (the latter is a `@gorhom/bottom-sheet`, a different component, confirmed by reading its own doc comment distinguishing it from `BottomSheetModal`). The quick-menu popover in `app/index.tsx` (lines 1096-1133) that *does* immediately call `router.push` after closing (`handleOpenArchive`/`handleSettingsPress`) is deliberately a plain `<View>`, not a `<Modal>` — exactly the already-established fix pattern from the Quiet Corner/TodosOverlay bug history, correctly applied here too.
- **`useToDos()` (`hooks/useToDos.ts`) has no cleanup gaps.** Its three refresh triggers (mount effect, `subscribeToToDosChanged` effect, `useFocusEffect`) were traced individually — the subscription effect correctly returns the unsubscribe function, and none of the four write wrappers (`addToDo`/`updateToDo`/`completeToDo`/`deleteToDo`) can double-fire from a fast navigate-away-and-back, since each is a plain async function re-invoked fresh per call, not a re-entrant listener.
- **`useChatSession.ts`'s re-entrancy guard is real**, not just documented: `isSendingRef` (a plain ref, checked and set synchronously before any `await`) genuinely closes the double-RAG-response race the code's own comment describes — confirmed both `ask()` (line 164-185) and `submitQuery()` (line 187-213) check-and-set it before their first `await`.
- **`app.json`'s `"orientation": "portrait"` lock** (line 6) means the Activity is never destroyed/recreated for a rotation event at all, sidestepping the entire "state lost on `configChanges`" bug class for rotation specifically — confirmed no custom `android.configChanges` override exists that would suggest a rotation-recreate path was ever anticipated.
- **`TodosOverlay`'s undo-window flush-on-unmount is correct** (`components/TodosOverlay.tsx:107-112`): the `useEffect(() => () => flushPending(), [flushPending])` genuinely commits any still-pending completion if the overlay closes inside the 3-second undo window, preventing a completion from being silently dropped.
- **`OnboardingSetupScreen`'s memory-pressure watcher (`watchForMemoryPressure`) is correctly unsubscribed** on unmount (line 183-184, `stopWatching()`), and the `runCompletionSequence` effect's `cancelled` flag (lines 203, 222, 228, 232, 240-242) correctly gates every `setState` call after an `await`, preventing a state update after unmount if the screen were ever torn down mid-sequence (it currently isn't, in practice, since `RootLayout` unmounts it only once `onComplete` fires from a user tap, but the guard is correctly in place regardless).
