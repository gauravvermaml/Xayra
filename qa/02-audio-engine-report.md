## Narrative

### The "single active audio source" invariant is enforced asymmetrically

Two enforcement mechanisms exist and both work correctly in isolation:
- `playUri()` (`player.ts:96-98`) calls `stopSpeech()` before loading a track — playback correctly interrupts TTS.
- `speakText()` (`tts.ts:28-34`) calls `stopSpeech()` before speaking — TTS correctly interrupts other TTS.
- `useChatSession.ts`'s `ask()` (line 171) and `submitQuery()` (line 195) both call `stopSpeech()` before running a new RAG exchange — a new question correctly interrupts a previous answer being read aloud.

But **nothing** in the codebase ever calls `pausePlayback()`/`releasePlayer()` from `speakText`/`speakTextAndWait`, and **nothing** in `recorder.ts` or `activeMode.ts` calls `stopSpeech()` or `pausePlayback()` before opening the mic. The invariant is real and mostly-true for TTS↔note-playback, but was never extended to cover recording (manual or Handsfree) as a fourth competing source at all. This is the root cause of findings #1-#3 above.

### Wake-word mic session: mutual exclusion with manual recording is correctly implemented

Unlike the TTS/playback gaps above, the one mutual-exclusion pair that **was** deliberately engineered — manual recording vs. Handsfree — is implemented correctly in both directions and confirmed still intact:
- `handleRecordPress` (`app/index.tsx:684`): `if (recorder.isTransitioning || activeMode.isActive) return;` — refuses to start a manual recording while Handsfree owns the one native capture session.
- `handleToggleHandsfree` (`app/index.tsx:777`): `if (!activeMode.isActive && (recorder.isRecording || recorder.isTransitioning)) { showToast(...); return; }` — refuses to engage Handsfree while a manual recording is using the session.

This is the Build 22 fix referenced in the code's own long comment block (`app/index.tsx:598-637`) and it still holds.

## Wake-word regression check (named, against current code)

All five previously-fixed bugs from the closed Build 33 root-cause chain (`PROJECT_STATE_HANDOFF.md` lines 148-154) were re-verified by reading the **current** `services/audio/activeMode.ts` and `services/ai/localWhisper.ts` — not by trusting the changelog.

1. **`[BLANK_AUDIO]`/non-speech marker leaking into saved transcripts** (orig. fix `ad83749`) — **STILL FIXED.** `localWhisper.ts:32-37` (`NON_SPEECH_MARKER_PATTERN`, `stripNonSpeechMarkers`) still strips `[blank_audio]`/`[silence]`/`(silence)`/etc. wherever they land in the string, applied unconditionally in `transcribeAudioLocal` (`localWhisper.ts:192`).
2. **Fixed VAD loudness floor couldn't hear speech from 2-3m away** (orig. fix `ad83749`) — **STILL FIXED.** `activeMode.ts:61-78` still defines the adaptive calibration constants (`MIN/MAX_SPEECH_RMS_THRESHOLD`, `SPEECH_ABOVE_FLOOR_MULTIPLIER=2.5`, `NOISE_FLOOR_CALIBRATION_MS=300`), and `handleAudioChunk` (`activeMode.ts:323-354`) still computes `speechRmsThreshold` from the first 300ms of each cycle rather than a hardcoded constant. **Caveat**: Finding 2 above shows this calibration window can be corrupted by a concurrently-playing TTS/note-audio source that the current code doesn't stop first — a new, adjacent risk to this exact mechanism, not a reversion of the original fix itself.
3. **Hardcoded wake-word spelling list → Levenshtein fuzzy match** (orig. fix `03f2a9d`) — **STILL FIXED.** `activeMode.ts:144-194` (`containsWakeWord`, `levenshteinDistance`, `MAX_EDIT_DISTANCE=2`) is unchanged in mechanism from the documented fix.
4. **"Hey Xayra" being erased, not misspelled → `initial_prompt` priming** (orig. fix `d70fdef`) — **STILL FIXED.** `localWhisper.ts:146` (`const INITIAL_PROMPT = "Xayra"`) is still passed into `context.transcribe(fileUri, { language: "en", prompt: INITIAL_PROMPT })` at `localWhisper.ts:189`.
5. **No gain normalization → onset-softness losing the first syllable** (orig. fix `a80f813`) — **STILL FIXED.** `wav.ts:93-136` (`normalizePcmGain`, `TARGET_PEAK_RATIO=0.9`, `MAX_GAIN=8`) is still called unconditionally from `writePcmChunksAsWav` (`wav.ts:143`), shared by both the manual recorder and Handsfree.
6. **Native mic session torn down/rebuilt before every utterance** (orig. fix `726e401`) — **STILL FIXED.** `activeMode.ts:269-296` (`start()`) still opens `AudioRecord` exactly once; `armListening()` (`activeMode.ts:356-382`) is confirmed to touch only the JS-side `capturing` flag and never calls `AudioRecord.init()`/`.start()` again; `finalizeUtterance()` (`activeMode.ts:408-441`) likewise never calls `AudioRecord.stop()`.

**Verdict: all 5 confirmed still fixed, no regression found in any of them.**

**Candidate #6 (new)**: Engaging Handsfree, or an already-engaged Handsfree session, can have its mic input corrupted by TTS/note-playback audio that the current code never stops — see Findings 2 and 3 above. This isn't a reversion of any of the 5 fixes above; it's a new interaction surface (TTS/playback ownership never being extended to guard the recording layer) that specifically threatens the adaptive-VAD-calibration and no-echo-cancellation guarantees those fixes depend on. Two concrete sub-cases:
   - **6a**: TTS/playback already active *when Handsfree engages* → contaminates the first-cycle noise-floor calibration (Finding 2).
   - **6b**: TTS triggered *while Handsfree is already listening* (via the independent "Listen" button, which has no awareness of Handsfree at all) → the assistant's own voice is picked up as a live utterance mid-session, exactly the failure mode bug #5's `capturing`-flag design was built to prevent, but reached through a code path outside that design's scope (Finding 3).

## Known-safe, checked and fine

- `player.ts`'s single shared `AudioPlayer` instance (module-scoped, not per-component) genuinely guarantees at most one note track audible at a time (`player.ts:33-34`, `ensurePlayer()`).
- `useAudioPlayerControls`' reference-counted release (`player.ts:224-239`, `mountedConsumerCount`) correctly tears down the native player only once the last mounted consumer unmounts, without one card's unmount killing a sibling's still-active playback.
- `finishUtterance`'s `finally` block (`app/index.tsx:579-593`) unconditionally deletes the raw WAV and resets processing/pipeline state on every code path (success, too-short, silent, no-wake-word, duplicate, cancel) — no leaked temp file, no stuck "processing" state found on any traced early-return.
- The Build 39 "stop, don't execute" cancel gesture (`app/index.tsx:687-700`, `cancelRequestedRef`) correctly no-ops the pipeline before a note/query is created and doesn't leave a stray file (falls through to the same `finally` cleanup above).
- `wav.ts`'s `normalizePcmGain` (`wav.ts:103-136`) is gain-clamped in both directions — `MAX_GAIN=8` prevents blowing up a near-silent buffer into hiss, and the sample-scaling loop clamps to `[INT16_MIN, INT16_MAX]`, so no wraparound/overflow is possible.
- `asrRouter.ts`'s Tier 1/Tier 2 fallback (`transcribe()`, lines 176-199) correctly consumes and nulls `activeSession` exactly once per call — no double-consumption or reentrancy hole found in the Tier-1-to-Tier-2 handoff.
- To-do reminder notifications never trigger any in-app audio: `subscribeToToDoNotificationTap`'s handler (`app/index.tsx:195-197`) only calls `setIsTodosVisible(true)` — no TTS, no playback, so this cannot collide with an active audio source (confirmed no `speakText`/`playUri` call anywhere in `services/notifications/`).
- Recording ⟷ Handsfree mutual exclusion (the one pairing that was actually engineered) is correct in both directions — see narrative section above.
- The CPU-contention gate *mechanism* itself (`isTranscriptionInProgress()` counter in `localWhisper.ts:58-62`, incremented/decremented around the one real transcription call) is race-safe as a counter — the only issue found is the fixed retry bound (Finding 4), not the counter's own correctness.
